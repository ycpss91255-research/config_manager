# 驗收報表的三種狀態與人工簽核

`script/acceptance.sh` 的報表怎麼分「自動檢查」與「人工待驗」、人工項目怎麼簽核、發布閘門看什麼、目標版本從哪裡來。依據是維護者在 #355 的定案（2026-11-14 兩則：發布閘門與人工項目、目標版本；簽核格式先在 #355 訂成文件，#373 的 release 層之後引用同一份）。

檢查點與規格的對照仍在 `doc/acceptance-checkpoints.toml`；這份只講多出來的規則。

## 檢查點的三種

| 種類 | 對照表裡怎麼寫 | 判定 |
|---|---|---|
| 自動 | `specs` 指到規格 | `acceptance.sh` 實際執行那些規格：通過或未通過 |
| 人工 | `manual = true`，`specs` 必須是空的 | 有合格的簽核紀錄就是「已簽核」，沒有就是「人工待驗」 |
| 未涵蓋 | `specs` 是空的，也沒有 `manual = true` | 未涵蓋，**不是通過** |

- 人工檢查點是「只能由真人驗收」的那一種，例如 v0.9.0 第 2 條（未參與開發的同事操作，U42）、v0.10.0 第 1 條（實際使用兩週）。
- 頁面互動的行為，能用 Playwright 自動化驗證的，就寫成規格，**不標人工**（維護者 11/14 的原則）。
- 一條檢查點同時有 `specs` 與 `manual = true`，是對照表寫錯：`acceptance.sh` 以 2 結束。

## 簽核紀錄的格式

簽核寫在那一條人工檢查點底下：

```toml
[[milestone.checkpoint]]
number = 2
text = '…'
manual = true

[milestone.checkpoint.signoff]
by = '姓名 <email>'
date = 2026-12-01
evidence = 'https://github.com/ycpss91255-research/config_manager/issues/123#issuecomment-456'
summary = '誰、在什麼環境、照什麼步驟做了什麼，結果如何'
```

| 欄位 | 規則 |
|---|---|
| `by` | 簽核的人，`姓名 <email>`。不能是空的 |
| `date` | 驗收完成的日期，TOML 的日期型別（不是字串） |
| `evidence` | 指到實際驗收證據的網址：這個 repo 的 issue 或 PR（可以帶 `#issuecomment-…`）。證據本身要附在那裡（CLAUDE.md：關閉帶驗收條件的 issue 時，證據附在 issue 上） |
| `summary` | 一句話說明做了什麼、結果。不能是空的 |

工具會擋下的：

- 簽核寫在不是人工的檢查點上（自動或未涵蓋）：`acceptance.sh` 以 2 結束。**簽核不能把沒做的驗收變成通過**，也不能取代規格。
- 缺任何一個欄位、欄位是空的、`date` 不是日期、`evidence` 不是這個 repo 的 issue 或 PR 網址：以 2 結束，並指名是哪一條、哪一欄。

工具擋不住的（要人看）：

- 工具只核對簽核的格式與 `evidence` 網址的形狀，**不核對那個網址的內容真的是這一條檢查點的驗收證據**。這與 `script/lint_checkpoints.sh` 只確認「有一筆真的 commit 被記在那一行」是同一種限制。
- 把一條其實可以自動化的檢查點標成人工，在 diff 上看得到，但工具不擋。

## 報表

`acceptance.sh` 的報表分三段，每次都印出來：

1. **自動檢查**：每一條自動檢查點的判定（通過／未通過），以及未涵蓋的檢查點。
2. **人工待驗清單**：每一條人工檢查點，是「人工待驗」，還是「已簽核」（附 `by`、`date`、`evidence`）。
3. **整體**：自動檢查全部通過、沒有未涵蓋、人工檢查點全部已簽核，才是「整體通過」。**只要還有一條人工待驗，就是整體未通過。**

## 結束碼與閘門

`acceptance.sh` 多一個選項 `--gate`：

| `--gate` | 結束碼 0 | 結束碼 1 | 結束碼 2 |
|---|---|---|---|
| `overall`（預設） | 整體通過 | 整體未通過（含人工待驗） | 對照表本身有問題（含簽核格式錯） |
| `automated` | 自動檢查全部通過、沒有未涵蓋（人工待驗不影響） | 自動檢查有未通過或未涵蓋 | 同上 |

- **發布閘門看整體**：`script/release.sh` 不帶 `--gate`，用的就是預設的 `overall`，判定不用改。人工待驗時，正式 tag 不會建立 release；rc 仍會建立，標題寫未通過。擋下正式 tag 時，訊息除了未通過與未涵蓋，也逐條列出人工待驗的檢查點。
- **main 上的 `acceptance` job 用 `--gate automated`**：它要抓的是自動檢查退步與對照表壞掉；人工項目要等真人，不應讓 main 一直是紅的。報表照樣印出三段，人工待驗看得到。
- 兩種閘門印出的報表相同，只差結束碼怎麼算。

## 目標版本

- 對照表頂層寫 `target = 'vX.Y.Z'`：目前的目標版本。來源只有這一個，不查 GitHub 的 milestone。
- `acceptance.sh --target`：跑 `target` 指的那一版。main 上的 `acceptance` job 用 `--target --gate automated`，不再寫死版號。
- **防呆**：`--target` 時，如果目標版本已經整體通過，而對照表裡它之後還有別的版本（`id` 是 `vX.Y.Z` 的 milestone；`core-flow` 這種不算版本），就以 2 結束，並指名下一版——目標版本該推進了，留在已完成的版本上，等於這個 job 永遠報綠（與原本寫死 `v0.1.0` 是同一個問題）。
- `target` 沒寫、寫的版本不在對照表裡：以 2 結束。

## 與其他工作的關係
