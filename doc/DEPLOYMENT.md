# 部署

把 config_manager 起在一台機器上要知道的事。決策的理由在 ADR-00000031；這份只講怎麼做。

## 起服務（現場）

`compose.yaml` 單獨就是現場用的那一套：正式映像、部署模式、只有本機連得到、當掉會自己起來。

1. 決定這台機器上 config 所在的根目錄，寫進 repo 根目錄的 `.env`（不進版控）：

   ```
   CM_TARGET_ROOT=/opt/robot/config
   ```

   這個目錄要先存在。它同時決定「掛進容器的是什麼」與「白名單放行什麼」。`just docker run` 起之前
   會檢查它在不在；檢查的是 `docker compose config` 解出來的那一個，與 compose 實際掛載的相同——
   shell 的環境變數優先於 `.env`，兩者都沒設才用預設的 `/opt/robot/config`。訊息會寫出採用的目錄與
   它的來源（#388）。

2. 建置並啟動：

   ```bash
   just docker build
   just docker run
   ```

   `just docker run` 除了 `docker compose up -d`，還在主機上做兩件事（#385）：起之前檢查舊的
   `CM_HOSTNAME`（見下面「從舊版升級」），起之後讀這台機器的 `hostname`、交給服務當「本次啟動
   取得的候選」。直接用 `docker compose up -d` 也起得來，但沒有候選（設定頁會顯示目前主機名稱尚未
   確認），主機端的舊變數也檢查不到。啟動工具不檢查服務是否就緒；它說「Compose 啟動命令完成」
   時，服務是否正常要看 `docker compose ps`。

3. 在**這台機器上**開 `http://localhost:8081`。

4. 第一次納管之前，以開發者身分到「設定」確認「新納管預設主機名稱」：預填本次啟動取得的候選，
   沒有候選就直接輸入。保存的值存在設定庫的清單檔（`config-list.toml` 的 `[defaults] hostname`），
   之後每一筆納管都用它；它**不修改已納管項目的 hostname**。還沒保存時不能納管，其餘照常。

## 新納管預設主機名稱與服務重啟

- 候選只對**本次服務啟動**有效。容器自己重啟（`restart: unless-stopped`、`docker restart`、主機
  重開機）之後，設定頁顯示目前主機名稱尚未確認——重跑 `just docker run` 就會取得（容器沿用時
  不會重啟服務）。已保存的名稱不受影響，納管照常。
- 同一次服務啟動已有候選時，重跑 `just docker run` 不更新它：它是「本次啟動取得的候選」，不保證
  是即時的主機名稱。
- 候選放在容器裡的 `/run/config_manager/`，不在設定庫、也不在資料卷，容器每次啟動時清空；現有的
  `git bundle` 備份、資料卷打包、設定庫複製都不包含它。保存的名稱在清單檔裡，所以會隨備份與
  還原走——還原到另一台機器時，先到設定頁確認它是不是這台的名稱再納管。
- CLI 還沒有對應的指令（排在 v0.10.0）；確認與修改只能在介面上做。

## 從舊版升級：`CM_HOSTNAME`

#385 起名字不再由 `CM_HOSTNAME` 決定，compose 也不再把它傳進容器。照這個順序：

1. **移除舊變數**：`.env` 裡的 `CM_HOSTNAME=…`、shell 設定檔裡的 `export CM_HOSTNAME=…`、
   自訂 compose 檔或 `docker run -e` 裡的 `CM_HOSTNAME`。
2. **重新啟動服務**：`just docker run`。
3. **到介面「設定」確認新納管預設主機名稱**。既有條目的 hostname 全部相同時，設定頁會把它列成
   名稱來源之一；與本次啟動取得的候選不同時兩個都列出、不自動選，由開發者確認。既有條目不改名。

留著舊變數時會停下來並指出如何移除：啟動工具檢查它自己的環境變數與 repo 根目錄的 `.env`
（`.env` 當文字逐行讀、不執行；`export` 寫法與空值都算；`#` 開頭的註解不算；不檢查
`--env-file`、`COMPOSE_ENV_FILES` 指定的其他檔），服務檢查容器自己的環境（空值也算）。直接用
`docker compose up` 時主機端檢查不到——名稱不受影響，因為服務已不讀它。

## 不改動主機系統、以非 root 執行

這套服務只需要 `just`、`docker`、`git`：啟動、停止、備份、還原都不在主機上安裝軟體、建立服務、寫入
`sudoers` 或改系統設定。服務容器以非 root 的服務使用者執行，只管理掛進容器、而且它寫得進去的目錄；
目標目錄由你建好、設好權限。目標檔案的擁有者或權限設不上時，系統照實標記，不會為了寫得進去而提權。
將來若要管理 `/etc` 這類由 root 擁有的系統級目錄，會是明確打開才生效、能完整移除的獨立方案。決策與
理由見 [ADR-00000034](adr/00000034-non-privileged-and-no-host-changes-by-default.md)。

## 只有本機連得到

前端（8081）與後端（8080）都只聽 `127.0.0.1`。從區網上別台機器連不到，這是刻意的：
這個服務**沒有密碼**，身分與角色是自己填的——聽在區網上，等於區網上任何人都能改這台機器的
config。所以沒有「開放區網」的設定可以開。

### 從別台機器操作：SSH 通道

在**你自己的電腦**上開一條通道，把兩個埠都帶過來（頁面在 8081，它會去連同一個主機名的 8080）：

```bash
ssh -N -L 8081:127.0.0.1:8081 -L 8080:127.0.0.1:8080 <使用者>@<那台機器>
```

通道開著的時候，在你自己的電腦上開 `http://localhost:8081`。誰連得進來由 SSH 的認證決定。
關掉那個 `ssh` 就斷線。

## bridge 網路

預設是 `host` 網路，因為 bridge 會讓同一台機器上的 ROS 2 discovery 靜默失效。確定不受影響、
而且需要容器之間隔離時，疊上 `compose.bridge.yaml`：

```bash
just docker bridge run
```

- **主機名稱不靠容器讀。** bridge 下容器自己的名稱是每次重建都換的容器 ID；`just docker bridge run`
  的 post-run hook 在**主機**上讀 `hostname` 當候選，開發者在設定頁確認後才保存（#385）。不再需要
  `CM_HOSTNAME`。
- 埠號對應的主機端一樣只綁 `127.0.0.1`，所以「只有本機連得到」不變，遠端操作同樣走 SSH 通道。
- 同一台機器上其他掛在 docker 預設網路的容器連得到這兩個服務。
- 要查「請求到底有沒有到後端」時，設 `CM_ACCESS_LOG=1` 再起：後端每個請求在 `docker logs` 記一行
  （時刻、方法、路徑去掉 query string、狀態碼、毫秒數），不記 cookie、token、header、body。平常不設（關）。

## 開發

疊上 `compose.dev.yaml`：開發映像、開發模式、主機的 `src/` 掛進容器、不自動重啟。

```bash
just docker dev build
just docker dev run
```

想讓這台機器上每一道 `docker compose` 與 `just docker …` 都自動帶上它，在 `.env` 寫
`COMPOSE_FILE=compose.yaml:compose.dev.yaml`。

## 重啟之後什麼還在

容器重啟、移除重建、機器重開，結果相同：

| 還在 | 不在 |
|---|---|
| 納管清單 | **還沒進版的草稿** |
| 已進版的來源內容 | 輸入過的身分（要重新輸入） |
| 變更歷史 | 編輯權（沒有人持有，誰先編輯誰取得） |
| 白名單 | |

目標檔案的狀態（一致／偏離／未部署）在重啟後當下重新比對，不是沿用重啟前的結果。

**草稿只留在服務的記憶體裡。** 改到一半要停服務之前，先在頁面上按「進版」；沒進版的改動
重啟後就沒了，救不回來。頁面在儲存草稿時也會說這件事。

留得下來的東西住在 `config_repo` 這個 volume。`docker compose down`（或 `just docker stop`）
**不會**刪它；`docker compose down --volumes` 會——那是唯一真實來源，刪之前先備份。

## 只跑一個後端

**後端只能跑一個行程**：不要開多個 worker，也不要把後端開成多個副本（compose 的 `scale`、
`replicas`）。編輯權（一次只有一個人能改）、草稿與輸入過的身分都在那一個行程的記憶體裡；
「檢查編輯權」和「寫入」也靠行程內的一把先到先處理的鎖排隊、不交錯（F23）。開成兩個行程，兩邊各有一份
編輯權，就會兩個人同時在改。`config_manager serve` 把 app 物件直接交給 uvicorn，本來就只會
起一個行程；compose 檔也沒有設副本。

## 備份與還原

設定庫（`config_repo` 這個 volume）是唯一真實來源：納管清單、每一份的來源內容、白名單、全部的變更歷史
都在裡面。它壞了或不見了，這套系統就不知道任何一台機器該長什麼樣。

**這不是整機備份。** 備份的只有設定庫裡**已經進版**的東西：

| 在備份裡 | 不在備份裡 |
|---|---|
| 納管清單 | **目標檔案**——機器上實際被管理的那些設定檔 |
| 每一份的來源內容 | 還沒進版的草稿 |
| 白名單 | 輸入過的身分、編輯權 |
| 全部的變更歷史 | |

目標檔案不備，是因為它們可以從設定庫寫回去；要保住整台機器的設定目錄，那是另一套備份。

### 備份

服務**不必停**，隨時可以做：

```bash
just docker backup /path/to/backups
```

（或 `script/backup.sh /path/to/backups`。）資料夾不存在會建。做出來的是一個檔案，例如
`config-repo-20261013T012345Z-a1b2c3d.bundle`——檔名是時刻與那一版的識別碼。

指令說「備份完成」的時候，那個檔案已經被**實際還原過一次**確認還原得出來，不只是檔案存在。
正在進版的時候備份也沒關係，拿到的一定是某一個完整的版本。

把備份檔放到**另一台機器或另一顆磁碟**上。放在同一顆磁碟上的備份，磁碟壞的那天會一起不見。

### 還原

還原之前要滿足兩件事，少一件指令就拒絕、什麼都不動：

1. **服務已經停了。**

   ```bash
   docker compose stop
   ```

2. **設定庫是空的。** 還原不會覆蓋、也不會替你清空既有的設定庫。設定庫已經不見（volume 壞了、換了
   機器）的話它本來就是空的；要拿備份**換掉**一份還在的設定庫，得先自己把舊的 volume 移走——那一步會
   讓現有的資料消失，所以不由指令代做。

然後：

```bash
just docker restore /path/to/backups/config-repo-20261013T012345Z-a1b2c3d.bundle
docker compose up -d
```

指令先確認備份檔還原得出來，才開始動設定庫；備份檔壞了就停在那裡，設定庫維持空的。中途失敗的話
設定庫會被清回空的，不會留下半份看起來像好的。

### 還原之後

還原回來的是設定庫。**機器上的目標檔案沒有被動過**，所以啟動後到頁面按「檢查差異」，系統會拿
還原回來的來源重新比對：

- **一致**：目標檔與備份當時的來源相同，不用做什麼。
- **未部署**：目標檔不見了。展開那一份、按「寫出到目標」補回來，內容與擁有者、權限都照設定庫的紀錄。
- **偏離**：目標檔在備份之後被改過。**系統不會自動覆寫它**——到差異檢視決定要「以來源覆蓋目標」
  還是把現場的修改收進來。

備份之後才進版的修改不在備份裡。那些修改寫出去的目標檔，還原後會顯示為偏離，由人決定去留。

## 起不來的時候

現場那一套設了 `restart: unless-stopped`：服務當掉、或啟動檢查沒過，docker 會一直重試。
頁面打不開時照這個順序：

1. **看狀態。** `Restarting` 就是起不來、正在重試：

   ```bash
   docker compose ps
   ```

2. **看原因。** 啟動檢查的訊息以 `entrypoint:` 開頭，會說哪裡不對與下一步：

   ```bash
   docker compose logs --tail 50 backend
   ```

3. **停止重試。** 手動停掉的服務不會再被拉起來，日誌也不會繼續被洗：

   ```bash
   docker compose stop
   ```

4. 照第 2 步的訊息修正（最常見：`CM_TARGET_ROOT` 指的目錄不存在、白名單指到容器看不到的路徑），
   再 `docker compose up -d`。

`docker compose stop` 之後服務會一直停著，連機器重開也不會自己起來，直到再 `up` 一次。
