# 手寫 changelog 只記版本里程碑，不記逐次變更

> 服務：不變式 9

- **Date:** 2026-09-08
- **Status:** Accepted
- **Relates to:** ADR-00000028（紀錄以中文書寫）、`#142`（本決定的來由）、`#124`（補寫那一次的落後）

## Context

`doc/changelog/CHANGELOG.md` 先前以「能力／逐次變更」為粒度：一條 bullet 涵蓋數個
commit，按 `Added` ／ `Changed` ／ `Fixed` ／ `Notes` 分節。維持它與 `main` 一致的
唯一機制是**人記得寫**，而漏掉不會發出任何訊號——那正是不變式 2 的靜默失敗被寫進
文件裡。

這不是假設：2026-09-05 的補寫（`#124`）落後了 **37 個 commit**，而缺口是在一張
「它沒被記得」的 issue（`#142`）還開著的期間繼續長出來的。

工具擋不住這種落後，兩種都評估過：

- **一支 lint 比對 `git log` 與 changelog 的缺口。** 做不到——粒度**刻意**不是一個
  commit 一條，機器算「缺口」需要一條把 commit 對到 bullet 的機器可讀關聯，而那條
  關聯不存在。硬做就要為每個 commit 加一個 changelog 標記，成本從「記得寫」換成
  「記得標」，同一個機制換個地方失效。
- **「動到 `src/` 就要求動到 `CHANGELOG.md`」的路徑檢查。** 做得到，但它檢查的是
  那個檔案有沒有被改、不是改得對不對（與 `#125` 揭露的 `lint_adr` 缺陷同一類），
  還會誘發為了轉綠而補一行敷衍的紀錄——比沒有紀錄更糟，因為它讓檔案看起來是被
  維護的。

依設計 §0.4「無法自動檢查的規範等同不存在」，剩下的路不是把規範寫得更用力，而是
**讓需要被維持一致的東西變少**（不變式 9）。

## Decision

手寫 changelog **只記版本里程碑**：一個版本一筆，記這一版對使用者的意義，在
milestone 關閉時寫。逐次變更的細節不在這裡。

意圖與理由各有去處，沒有無家可歸：

- **為什麼長成這樣** → `doc/adr/`
- **一次變更做了什麼與為什麼** → commit 內文（本 repo 的 commit 內文非常詳細）
- **目前能做什麼** → README 的「目前狀態」
- **還缺什麼** → GitHub milestone 與 issue

`60e1a07` 已經對 README 的 milestone 一節做過完全相同的判斷，理由也是「不要在旁邊
複製一份」。

## Consequences

- changelog 的更新頻率與 milestone 對齊（那個頻率人維持得住），不與每個 commit 對齊。
- 它保留了不變式 9 承認有價值的那一半——**這一版對使用者的意義**，那確實是產生器
  做不出來的；丟掉了產生器做得更好的那一半——逐次變更的清單。
- 讀者一版讀一段；要逐次變更的細節，`git log` 一步之遙。
- 仍然沒有工具擋它落後（里程碑粒度下也沒有機器可檢查的關聯），但會漂的表面已經
  縮到極小——一版一段的東西，落後看得出來。

## Alternatives

- **刪掉 changelog，發版要的東西全由 `git log` 產生（`#142` 選項 1）。** 否決：
  里程碑層級「這一版對使用者的意義」是產生器做不出來的那一半，刪掉會連它一起丟。
- **保留逐次變更粒度，加「動到 `src/` 就要求動到本檔」的 lint（`#142` 選項 3）。**
  否決：檢查存在不檢查成立，且誘發敷衍紀錄；上面 Context 已展開。
