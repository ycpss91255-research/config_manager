# 後端用 Python，因為原樣寫回的函式庫在那裡

> 服務：機制，無對應不變式

- **Date:** 2026-09-05
- **Status:** Accepted
- **Relates to:** ADR-00000013（型別參數欄位，不編輯檔案文字）、ADR-00000004（清單檔採 TOML）

## Context

設計文件 §3.2 的技術選型表寫了後端語言是 Python 3.11+，理由欄兩句：round-trip
parser 生態最完整，以及與既有 ROS 2 工具鏈一致。**那是一行表格，不是一份決策紀錄**
——它沒有寫下被否決的選項，也沒有寫下這個決定靠哪一句支撐。於是它被重新問了一次
（2026-09-05），而重新問的人手上沒有任何可以據以判斷的東西。

**這份 ADR 更正了那兩句的配重。**

**服務對象是 config 檔案本身，不是機器人。** 機器人是其中一種部署場景，不是選型
依據。因此原理由的後半句（ROS 2 工具鏈、未來接 `rclpy`）**降級為場景說明，不再是
支撐這個決定的理由**。查證也支持這個降級：ROS 2 官方維護的 client library 是
C++、Python、Rust；Go 的 `rclgo` 是社群的 CGo wrapper，多個分支且至今不完全可用。
一個不官方的綁定不足以成為選語言的理由——不論往哪個方向。

## Decision

**後端用 Python，唯一的支撐理由是 lossless round-trip 的函式庫生態。**

這個系統的核心保證是「編輯之後，沒被動到的東西逐位元組不變」。`doc/TEST-PLAN.md`
的 T6 把它寫成可驗的形式：

> parse → dump 未改動任何值時，**輸出與輸入逐位元組相同**；改動一個值後，
> **註解、引號樣式、鍵順序、縮排全部保留**；**四種格式（yaml／json／toml／ini）
> 各自通過上述**。

Python 這邊三個函式庫就是為此而生：`ruamel.yaml`、`tomlkit`、`configobj`。
`tomlkit` 已經在 T1 通過逐位元組的往返測試。

**換掉 Python 的代價不是移植，是自己實作四種格式的 lossless parser**——那會成為
這個專案裡最大也最容易錯的一塊，而它不是這個專案要解決的問題。

## Alternatives

- **Go。** 單一靜態執行檔可讓映像從 279 MB 降到約 20 MB，對邊緣部署是真的好處。
  **但 round-trip 這一關過不了**：`gopkg.in/yaml.v3` 的文件明載重新編碼時原始文字
  表示不會被完整保留；`go-toml/v2` 的文件編輯已被移出正式需求，要 lossless 得靠
  第三方；INI 沒有等同 `configobj` 的成熟選項。而映像大小那個好處，在部署形態已經
  是容器、且目標機器上通常已有 Python 的情況下並不成立。
  **會讓這個選項翻盤的條件寫在這裡**：若哪天決定放棄「編輯後保留註解與格式」，
  天平會整個倒向 Go。但那等於放棄 ADR-00000013 與 T6 的前提。
- **Rust。** round-trip 的情況比 Go 好（`toml_edit` 是成熟的 lossless 實作），
  但 YAML 與 INI 仍有同樣的缺口，且開發速度對一個以「多方考慮、把每個功能測穩」
  為節奏的專案不划算。
- **Node／TypeScript。** `yaml` 套件的 round-trip 支援不錯，但 INI 與 TOML 的
  生態較弱，且會為前端引入一條這個專案刻意避開的打包鏈（§3.3：不需框架也不需
  打包流程）。

## Consequences

- 效能與並行不是這個決定的考量，因為這個系統沒有那種需求：讀一份小 TOML、算幾個
  sha256、`subprocess` 呼叫 git、服務單一編輯階段。任何語言都綽綽有餘。
- 部署映像維持在數百 MB 量級。可接受，因為部署形態是容器。
- **這個決定的存續繫於一個條件**：只要「原樣寫回」還是核心保證，它就成立；那條保證
  一旦被放棄，這份 ADR 應立即重新檢視。
