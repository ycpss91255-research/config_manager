# Identity is split into an immutable uid, a mutable name, and a hostname

> 服務：不變式 8（身分與命名一次解析，來自檔案）

- **Date:** 2026-09-02
- **Status:** Accepted

## Context

身分需同時滿足三個要求：穩定（路徑或內容改變時不變）、唯一、人可讀。
單一欄位無法同時滿足——機器要用的必須永不改變，人要看的必須隨時可改。

## Decision

拆成三個欄位：

- `uid`：由**匯入時刻的毫秒時間戳**轉 base36 產生（8 碼），**永不變更**。所有內部關聯只認它。
- `name`：由目標路徑最後二至三層推導，人可改。純粹給人看，過期不影響功能。
- `hostname`：**納管時讀取系統 hostname 寫入檔案，之後永不再讀**，人可改。

完整參照形式 `<name>@<hostname>-<uid>`。此模式取自 Kubernetes 的 Name／UID 分離：
UID 是系統產生的不透明值，保證在時間與空間上唯一；Name 由客戶端提供、鼓勵對人
友善，在特定範圍內唯一。

## Alternatives

- **內容雜湊當 id**：內容一改 id 就變，歷史直接斷裂。致命。
- **路徑雜湊當 id**：路徑一改 id 就變，繞回原點。
- **流水號**：需要「讀取當前最大值 +1」，多一個協調點。
- **隨機值**：需要碰撞檢查，且「產生 N 次不重複」這類驗證是機率性斷言，會偶發失敗。
  時間戳的唯一性來自單調遞增，不是機率——backend 是唯一寫入者，不存在競爭。
- **執行期讀取 hostname**：hostname 因重新配置或映像複製而改變時身分靜默改變；
  同映像開出的多台機器改名前 hostname 相同會撞號；repo 被 clone 到開發機時
  紀錄全部對不上；未來要在 A 機器管理 B 機器的 config 無法實作。
- **hostname 併入 id**：跨機比對時「同一份 config 的不同實例」會變成無關的兩筆。

## Consequences

- 唯一性由時間單調遞增保證。清單檔載入時的重複檢查保留，但角色是**防呆**
  （防手動編輯時貼錯），不是主要保證機制。
- uid 可排序，因此**納管順序被保留下來**，這是附帶效果而非設計目標。
- 毫秒而非秒：批次納管十個檔案會在同一秒內完成，秒級解析度會撞號。
- base36 而非可讀時間字串：後者 17 碼，出現在每一筆變更紀錄裡太長。
- 內容雜湊仍有用，但用於偏離偵測——那裡需要的正是「內容一改就變」。
