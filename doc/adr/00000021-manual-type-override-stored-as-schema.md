# 人工指定的型別存為 schema，並可逐欄位清除

> 服務：不變式 2（絕不靜默失敗）

- **Date:** 2026-09-02
- **Status:** Accepted
- **Relates to:** ADR-00000013

## Context

參數型別由納管時的推斷決定。但**推斷只能看到當下的值**：`timeout: 5` 會被推斷為
整數，而作者的意圖可能是浮點——這正是後續改成 `5.5` 時會出事的地方。

推斷是起點，不是答案。需要一條人工更正的路。問題是：更正的結果存在哪、怎麼撤銷。

## Decision

人工指定的型別**寫入該 config 對應的 schema 檔**。人工指定的型別就是 schema 的一部分。

型別來源三層，後者覆蓋前者：推斷（系統）→ 人工指定（開發者）→ 參數描述（未來，
從執行中的 ROS 節點取得；有此來源時優先於推斷，但不覆蓋人工指定）。

**逐欄位清除**，回到推斷值，不影響同一份 config 的其他指定。

僅開發者可改（ADR-00000020）。變更以 `meta` 類型記錄。

## Alternatives

- **存在獨立的 override 檔**：需要額外的合併邏輯與衝突處理，而 schema 本來就是
  「這個欄位是什麼型別」的權威來源，多開一個檔案等於有兩個真實來源。
- **存在清單檔**：清單檔描述的是「管了哪些 config」，不是 config 的內容結構。
- **全部重設而非逐欄位清除**：改錯一個欄位就要重來，會讓人不敢用這個功能。
- **開放給一般使用者**：改錯型別的後果是靜默的，直到 node 啟動失敗才會發現。

## Consequences

- 人工指定自動獲得版控，且**隨退版一併回退**——退回三個月前的版本時，型別定義
  也回到當時的狀態，不會用今天的 schema 驗舊內容。
- schema 檔可能同時包含自動產生與人工指定的內容，需要能區分。
- 未來導入 ROS 參數描述時，優先序已經定義好，不需重新討論。
