> **狀態：2026-09-04 逐項確認並修訂。**
> 已確認核心層七項介面，並套用四項核心修正（T1／T2／T4／T18）、將兩項檢查改置 IO 層

> 測試先行的規則是「**沒有經過確認的測試介面，不寫測試**」。已確認者進入 red → green 迴圈。

用語依 `CONTEXT.md`，測試名稱也應使用同一套詞彙。

## 什麼是「測試介面」

**測試介面**是「從哪個位置觀察行為」。同一段程式碼可以從很多位置觀察，
但只有公開介面這個位置是穩定的。

| 觀察位置 | 測試長什麼樣 | 好壞 |
|---|---|---|
| 內部實作 | 「有沒有呼叫 `chmod`？」「暫存檔名對不對？」 | **壞**。改寫實作就壞，但行為沒變 |
| 公開介面 | 「呼叫 `write()` 之後，目標檔案的內容與權限對不對？」 | **好**。內部怎麼改都不影響 |

**測不了全部**，所以事先議定測試介面，是讓測試力氣落在關鍵路徑與複雜邏輯上、
而不是散在每個邊界案例上的方法。

編號 `T1`–`T21` 為單元／整合／系統層（`T19` 是工具層，觀察 repo 自身的守門腳本），
`A1`–`A6` 為驗收層。

## 規格放在哪：目錄是層級，型別寫在檔名裡

設計 §3.6.1 把測試分成**三個正交軸**，而目錄樹只反映其中一個。

| 軸 | 值 | 表現在哪 |
|---|---|---|
| 1 靜態分析 | ruff／mypy／pylint／hadolint | `test/lint/<tool>/`——根本不是動態測試 |
| 2 **層級**（範圍） | unit／integration／system／acceptance | **目錄**：`test/pytest/<層級>/`、`test/bats/<層級>/` |
| 3 **型別**（目的） | smoke／end-to-end／regression | **檔名**：`entrypoint_smoke.bats` |

**只有四個層級，而且沒有第五個。** `test/bats/runtime/` 與 `test/bats/smoke/` 曾經
各自站在層級的位置上，兩者都不是層級（#116）。`runtime` 講的是「誰執行它」，
`smoke` 是軸 3 的型別。參照專案 `ycpss91255-docker/base` 的 `test/bats/` 底下也只有
那四個。

**「它在哪個目錄」與「誰執行它」是兩個獨立的問題，不該互相決定。**
§3.6.1 的軸 3 明文寫著 smoke「在 runtime-test stage 的建置過程中執行」——那是型別的
性質，不是它的位址。把執行者寫進目錄名稱，換來的是一個 PDF 裡不存在的層級。

| 規格 | 層級（目錄） | 型別（檔名） | 執行者 |
|---|---|---|---|
| `test/bats/system/entrypoint_smoke.bats` | system | smoke | `docker build --target runtime-test` |
| `test/pytest/system/test_api.py` | system | — | `script/test.sh` **與** `runtime-test`，同一份檔案 |

### 兩層級的現況與代價

**`test/bats/system/entrypoint_smoke.bats` 在別處會整檔跳過。** 它斷言的是建好的
runtime 映像（裝進去的 entrypoint、烤在 `/opt` 的原始碼、映像自己的 PATH），在工具
映像裡觀察到的是別的東西。守衛是 `CM_SYSTEM_IMAGE`——**一個與每條斷言都無關的旗標**，
不是「`/entrypoint.sh` 在不在」：後者正是第一條斷言的東西，拿它當守衛會讓那條斷言恆真。

**skip 的代價寫在這裡：一組永遠在跳過的規格，與「沒有規格」的差別只有輸出多幾行字。**
所以兩端都擋著它：`script/test.sh` 在結束前把每一條跳過的規格逐條列出（T19 有規格
釘住），而 `docker build --target runtime-test`——那組規格唯一該真的執行的地方——
在有任何一條跳過時**讓建置失敗**。少了後面那道，這個 skip 只是把紅燈換成靜默通過。

**`test/pytest/acceptance/` 是空的，而它在等的東西寫在這裡。** A1–A6 是瀏覽器操作的
使用者旅程，依賴的功能尚未實作（納管 #11／#9、驗證 #16、草稿與進版 #18、屬性與角色），
而**它們的執行通路本身也還沒有**——T11 沒有瀏覽器驅動，追蹤於 #99。所以這一層不是
「忘了寫」而是「寫不了」，並且：

- **A4 由另一個工作項目負責**，不在 #116 的範圍內。
- `script/test.sh` 每一次執行都會指名這一層沒有規格。一個「有四個層級」的框架實際上
  只有三個層級有東西，這件事必須從輸出看得出來，不是只寫在這份文件裡。

## 核心層（純邏輯，無 I/O，可在無檔案系統／無 git 下執行）

### T1 — 清單檔載入與寫回

```
load(text) -> ConfigList | 具名例外
dump(ConfigList, 原樣資訊) -> text
```

| 驗證的行為 | 為何在這裡測 |
|---|---|
| 合法清單檔可載入，欄位值正確 | 基本契約 |
| uid 重複 → 具名例外，訊息指出是哪兩筆 | 不變式 2 |
| 目標路徑重複 → 具名例外（寫出順序決定結果，是靜默 bug） | 不變式 2 |
| 目標含 `..` → 具名例外 | 逃逸防護 |
| format 非允許值 → 具名例外 | — |
| **無法辨識的欄位 → 具名例外，指出欄位與行號**（含 `warnings` 等內部欄位，防止由清單檔注入） | 不變式 2 ／ PDF §329（2026-09-04 檢討新增） |
| `(name, hostname)` 重複 → **警示而非例外**（uid 已保證唯一） | 警示與錯誤的分界 |
| **寫回未改動的清單檔，輸出與輸入逐位元組相同** | 清單檔本身也要原樣保留 |
| 新增一筆條目後寫回，**既有條目的註解、順序、引號樣式不變** | 同上 |
| **附加的新條目帶選填欄位（schema／requires_privilege／permissions）時，寫回後全數保留** | 不變式 2（PDF §4.3 選填欄位表；靜默丟欄位即靜默失敗） |
| **改動或移除既有條目後寫回 → 具名例外**（dump 目前只支援未改動與新增；靜默丟失改為大聲失敗，待 T6 式 round-trip 把手實作編輯／移除） | 不變式 2（2026-09-04 檢討新增） |

**不測**：TOML 語法本身（那是 parser 的責任）。

**為何 dump 在這裡而不在 T6**：T6 處理的是**被管理的 config**（四種格式），
T1 處理的是**清單檔本身**（固定為 TOML）。兩者的原樣保證各自獨立，混在一起會
使「哪個壞了」難以定位。

**T1 的「原樣資訊」是原始清單檔文字**：dump 以 tomlkit 重新解析後在其上套用變更
（與 T6 的 parse 回 `(資料, 原樣資訊)` tuple 形狀不同，但各自自洽）。

**來源檔案存在性移至 T15**：核心無 I/O，`load(text)` 不讀磁碟；「清單裡每筆來源檔
是否存在」改由啟動前置檢查逐筆驗證。

### T2 — 狀態判定

```
decide(target_exists, target_hash, source_hash) -> 一致 | 偏離 | 未部署
```

| 驗證的行為 |
|---|
| 目標不存在 → 未部署 |
| 雜湊相同 → 一致 |
| 雜湊不同 → 偏離 |
| 三種狀態的判定順序（先存在性、後內容） |

**這個測試介面刻意不讀檔**——雜湊由呼叫者算好傳入。因此它的測試完全不需要檔案系統，
這是核心層可測性的關鍵設計（ADR-00000011）。

**「未納管」不由此判定**：其定義是「不在清單檔中」（CONTEXT），在呼叫 decide 之前就由
清單成員查詢決定，故 decide 只回三種狀態。

**decide 不收 entry**：判定只依存在性與雜湊，entry 用不到；實作時移除以免未使用參數。

### T3 — 驗證

```
check(content, format, rules, schema?) -> [問題]   # 空清單 = 通過
```

| 層 | 驗證的行為 |
|---|---|
| 第 1 層 | `yes`/`no`/`on`/`off` → 問題，指出行號與建議寫法 |
| 第 1 層 | 前導零 `08`、科學記號 `1e3`、`1.10` 尾隨零 → 問題 |
| 第 1 層 | Tab 縮排、尾隨空白 → 問題，指出行號 |
| 第 1 層 | 重複 key → 問題，**列出該 key 的所有出現行號** |
| 第 2 層 | 型別不符 schema → 問題，指出欄位 |
| 第 2 層 | 超出數值範圍 → 問題 |
| 第 2 層 | **人工指定的型別優先於推斷型別** |
| 第 2 層 | **同一份 schema 驗 YAML / TOML / JSON 三種格式的等價內容，結果一致** |
| 第 3 層 | 跨欄位規則違反 → 警示（非錯誤），可 override |
| — | 合法內容 → 空清單 |

**每個問題都必須含檔案、行號／欄位、修正建議三要素**——這本身是被測的行為。

**不測**：底層 schema 函式庫的驗證邏輯。

### T4 — 白名單判定

```
decide(rules, path) -> 允許 | 拒絕(原因)
```

| 驗證的行為 |
|---|
| 白名單內的路徑 → 允許 |
| 白名單外 → 拒絕，原因指出未涵蓋 |
| `../` 逃逸至白名單外 → 拒絕（正規化後比對） |
| 相對路徑 → 拒絕（要求絕對路徑） |

**符號連結解析移至 T8**：readlink／realpath 是 I/O，核心只做正規化後的字面比對；
連結是否逃逸白名單在寫出時點（T8）以 realpath 解析後判定。

### T5 — 身分推導

```
derive_name(target_path) -> name
new_uid(now, previous=None) -> uid
```

| 驗證的行為 |
|---|
| `/opt/robot/navigation/params.yaml` → `navigation-params` |
| `/etc/docker/daemon.json` → `docker-daemon` |
| 底線轉連字號、去副檔名、去重疊層級 |
| uid 由匯入時刻的毫秒時間戳轉 base36 產生，長度 8 碼 |
| uid 的**值**由注入的時刻決定——期望值手算寫死，不用實作的算法重算 |
| 兩次連續呼叫產生的 uid **嚴格遞增**（可排序 = 保留納管順序） |
| 同一毫秒內的兩次呼叫不會得到相同值（後者遞增 1） |

**唯一性來自時間單調遞增，不是機率。** backend 是唯一寫入者，因此不存在競爭。
T1 的重複檢查保留，但角色是**防呆**，不是主要保證機制。

**new_uid 收前一個 uid**：同一毫秒內遞增 1 需要知道前值，而純函式不藏狀態
（ADR-00000011），故把前值當參數傳入（`previous`，預設 None ＝ 首次）。

不寫「連續產生 N 次無重複」這類斷言——那是機率性測試，會偶發失敗而程式碼完全正確。
**偶發失敗的測試比沒有測試更糟**：它訓練人忽略紅燈。

### T12 — 型別推斷與人工指定

```
infer_types(資料) -> {欄位路徑: 型別}
draft_schema(型別對照) -> JSON Schema 骨架
```

| 驗證的行為 |
|---|
| 各基本型別正確推斷（整數、浮點、布林、字串、陣列、物件） |
| **浮點與整數區分正確**（`1.0` → 浮點，`1` → 整數）——ROS 型別錯誤的來源 |
| 巢狀結構的欄位路徑正確 |
| 陣列推斷出元素型別；空陣列標示為未知 |
| 產生的骨架可被 schema 驗證器載入，且能驗過原始資料 |
| 人工指定型別後，該欄位的型別以指定為準 |
| **清除指定後，回到推斷值**（不是清成空值） |
| 逐欄位清除，不影響同一份 config 的其他指定 |

**不測**：推斷結果是否「符合作者原意」——那無從得知。人工指定存在的理由正是推斷做不到這件事。

### T13 — 編輯階段生命週期

```
author(姓名, email, 角色) -> 身分 | 具名例外
acquire(使用者, now) -> 階段 | 已被占用(持有者資訊)
renew(階段, now) -> 成功 | 已失效
release(階段)
sweep(now) -> [被回收的階段]
```

**身分（誰）與階段（誰正在編輯）是兩件事。** 身分輸入不是取得階段——使用者可以只是
看清單。以下前半是身分，後半是階段。

| 驗證的行為 |
|---|
| 合法的姓名＋email＋角色 → 身分，git 作者字串為 `姓名 <email>` |
| 姓名或 email 為空 → 具名例外 |
| **姓名或 email 含 `<`、`>` 或換行 → 具名例外** |
| 角色不在允許集合 → 具名例外 |
| **角色是自我宣告，不驗證**：宣告開發者就是開發者，記錄的就是宣告的值 |
| 無人持有時可取得 |
| 已被占用 → 拒絕，回覆含持有者姓名、email、開始時間 |
| 持有者釋放後，他人可立即取得 |
| **續期逾時後階段自動回收**，他人可取得 |
| 部署模式：閒置達設定時間後階段被回收 |
| 開發模式：不因閒置回收 |
| 已失效的階段續期 → 明確失敗，不靜默重新取得 |
| **階段逾時釋放時，草稿一併清除**，且回報「有 N 份草稿被清除」而非靜默丟棄 |

**必須注入時鐘。** 這個測試介面的**階段**部分行為全部與時間相關，若讀系統時間，測
「10 分鐘後逾時」就要真的等 10 分鐘。**這是設計要求，不是測試技巧**——讀系統時間的
實作無法被有效測試。身分部分不涉及時間，不收時鐘。

**`<`、`>`、換行為何是錯誤而非清洗掉。** 那三個字元會破壞 git 的作者字串
（`姓名 <email>`）：塞進去之後產生的 commit 作者是另一個人，或整個 commit 無法建立。
悄悄清洗會讓變更紀錄上的名字與使用者輸入的不同——而變更紀錄的用途正是「追溯到人」
（ADR-00000020），紀錄與事實不符比拒絕輸入嚴重得多（不變式 2）。

**不驗證 email 收得到信。** 這裡沒有認證機制（`CONTEXT.md`：不說「登入」），email 是
給人看的識別，不是聯絡管道。驗證它會暗示一個不存在的保證。

### T14 — 參數索引與搜尋

```
index(uid, 資料) -> [(uid, 參數路徑, 值)]
reindex(索引, uid, 資料) -> 索引        # 更新：先移除該 uid 舊項目再重新展平
unindex(索引, uid) -> 索引              # 解除納管：移除該 uid 所有項目
search(索引, 查詢, 範圍) -> [命中] | 具名例外
```

| 驗證的行為 |
|---|
| 巢狀結構展平成正確的參數路徑 |
| 陣列元素以索引納入路徑 |
| 依參數名稱搜尋，命中含 uid 與路徑 |
| 依參數值搜尋 |
| **搜尋範圍為「全部」時，命中為各範圍的聯集** |
| **指定範圍時，其他範圍的命中被排除** |
| **修改一個參數後重新索引，舊值不再命中、新值命中** |
| **解除納管後，該 uid 的所有項目從索引移除** |
| 查無結果回空清單，不是例外 |
| **搜尋範圍不在允許集合內 → 具名例外，訊息列出允許的三個值** |

**最後兩項是不同的兩件事（#119）。** 「查無結果」是查得到範圍、查不到內容，
是合法的空結果；「範圍不在允許集合內」是呼叫端給了一個不存在的範圍。兩者回同一個
空清單的話，使用者看到的是「找不到符合的參數」——一個看起來正常的結果——於是以為
那個參數不存在，然後去別的地方找。處置與 `core/config_list` 對 `format` 的處置同構。

更新與移除那兩項是索引最容易出錯的地方——**新增容易，移除與更新容易漏**。因此更新與移除各有
獨立函式（`reindex` / `unindex`），而非要呼叫端自己拼——讓「容易漏」的兩件事有明確歸屬。

### T16 — config 屬性與群組

```
update_attributes(uid, {名稱, 群組, 主機, 說明}) -> ConfigList | 具名例外
group_tree(ConfigList) -> 樹狀結構
```

| 驗證的行為 |
|---|
| 修改群組後，**樹結構依新群組重建** |
| 一份 config 屬多個群組時，**在每個群組節點下都出現** |
| 無群組的項目歸入「未分群」節點 |
| 父節點的狀態為子節點中最嚴重者（偏離 > 未部署 > 一致） |
| 修改名稱不影響 uid 與任何關聯 |
| 屬性變更以 `meta` 類型記錄，不與內容變更混在一起 |

### T17 — 角色權限

```
permits(角色, 動作) -> 允許 | 拒絕
```

| 驗證的行為 |
|---|
| 一般使用者：可修改參數值、退版、處置偏離、在既有白名單內納管 |
| 一般使用者：**不可**修改參數型別、維護白名單、編輯 config 屬性 |
| 開發者：上述全部允許 |
| 角色切換後權限立即生效，不需重新輸入身分 |

**角色是自我宣告，不是認證。** 本測試介面驗證的是**權限對照表本身正確**，
不驗證「無法偽造角色」——v0.10.0 前沒有那個保證，也不假裝有。

### T18 — 草稿與進版

```
save_draft(階段, uid, 內容) -> 階段 | 驗證問題
adopt_draft(階段, uid, 目標現況) -> 階段 + [警告]   # 偏離處置的「先納入、待修正」出口
promote(階段) -> [變更紀錄] | 驗證問題(指出哪一份的哪一項)
discard(階段, uid?) -> 階段
```

| 驗證的行為 |
|---|
| 儲存草稿**不產生變更紀錄、不寫到目標位置** |
| 儲存時跑第 1 層驗證，不通過則不存 |
| 多份草稿共存，各自獨立 |
| **進版時任一草稿驗證失敗 → 整批不進版**，錯誤指出是哪一份的哪一個參數 |
| 進版成功 → 每份 config 各產生一筆變更紀錄，且都在同一次操作中 |
| 捨棄變更後，草稿消失且來源與目標皆未改變 |
| 進版後草稿清空 |
| **草稿與四種狀態正交**：一份「一致」的 config 可以同時有草稿 |
| **adopt_draft 把目標現況載入草稿**：內容照載，回傳每個非法值的警告（檔案／欄位／原因／建議三要素），**不因非法而拒載** |
| adopt_draft 與 save_draft 的分界：**save_draft 擋第 1 層、adopt_draft 不擋但警告**——前者是人正在編輯、後者要把壞內容撈進來修 |
| adopt_draft 產生的草稿仍受進版約束：**含非法值時整批不進版**，改乾淨後正常進版，作者記為進版者（偏離內容因此被重新掛到真人身上） |

**不測**：草稿在階段間共享——本系統一次只有一個編輯階段（ADR-00000014）。

**寫出批次回滾移至 T9**：跨多份的原子寫出＋失敗回復牽涉 I/O，核心 `promote` 只產生
`[變更紀錄]` 這批資料並保證「任一驗證失敗整批不進版」；實際寫出與回滾由 T9（系統層、
真實容器）擁有。

## IO 層（adapter，以真實檔案系統與 git 測試）

### T6 — 格式解析與原樣寫回

```
parse(text, format) -> (資料, 原樣資訊) | 解析錯誤(行號)
dump(資料, 原樣資訊) -> text
```

| 驗證的行為 | 為何重要 |
|---|---|
| **parse → dump 未改動任何值時，輸出與輸入逐位元組相同** | 原樣保證的核心 |
| 改動一個值後 dump，**註解、引號樣式、鍵順序、縮排全部保留** | 同上 |
| **新增／刪除一個鍵、或重排 list 元素後 dump，未觸動的兄弟節點其註解、引號、縮排、順序全數保留**，新增／移動的元素以一致樣式渲染 | 結構性編輯的原樣保證（T11／A2 的 list 重排、A6 整理流程依賴） |
| 語法錯誤 → 解析錯誤含行號 | 不變式 2 |
| 四種格式（yaml / json / toml / ini）各自通過上述 | |
| `raw` 格式不解析，原文通過 | |

### T7 — 變更紀錄

```
record(uid, 類型, 說明, 作者) / history(uid, 類型過濾) / revert(uid, 版本)
```

| 驗證的行為 |
|---|
| 記錄後可於歷史中查得，作者正確 |
| 訊息格式為 `<類型>(<uid>): <說明>` |
| 以 `cfg` 過濾時，`revert` 與 `meta` 紀錄不出現 |
| 退版後歷史仍含全部先前紀錄（**未被截斷**） |
| 退版產生新紀錄而非移動指標 |
| **退版至版本 V 後，該 uid 在來源 repo 的內容等於 V 版當時內容**（以 `history()`／既有讀取介面驗證，非 `git log`） |

**測試方式**：對真實的臨時 git repo 操作，透過本測試介面驗證（`history()`），
**不直接跑 `git log` 檢查**——那是繞過介面驗證（反模式）。

### T8 — 原子寫出

```
write(目標路徑, 內容, 權限) -> 成功 | 例外
```

| 驗證的行為 |
|---|
| 寫出後內容正確、owner／group／mode 符合指定 |
| 目標已存在時被覆蓋 |
| **寫入過程中斷 → 目標維持原內容，不出現半殘檔案** |
| **目標路徑（或其父目錄）經 realpath 解析後逃出白名單 → 具名例外，且寫出不發生**；不靜默跟隨或改寫連結所指的檔案 |
| 目標目錄不可寫 → 具名例外（訊息含路徑＋原因＋下一步，不只說「操作失敗」） |
| **失敗後暫存檔也清不掉 → 具名例外，訊息同時帶原本的失敗與該暫存檔的路徑** |

「中斷」以在改名前注入失敗來模擬。

**最後一項是「清理失敗」，與「中斷不留半殘檔」是兩條不同的路徑（#121）。**
後者驗的是清理成功的樣子（目錄裡只剩目標檔），前者驗的是清理失敗時會發生什麼。
兩邊各有一半的要求：清理失敗**不得蓋掉**原本的失敗原因（否則使用者去修一個次要
問題），也**不得消失**（否則目標目錄逐次累積 `.config_manager-*.tmp`，而沒有人
被告知）。所以訊息同時說出兩件事，`__cause__` 指向原本的失敗。

**符號連結逃逸落於此**（原 T4 移入）：寫出是逃逸真正造成危害的時刻（ADR-00000003 警告
改名會把連結替換成一般檔案而靜默失效）。實作二選一：`write` 簽章補收白名單 rules，或在
其前置一個 realpath ＋ T4 守門函式；本測試介面驗證的是「逃逸被拒、寫出未發生」這個結果。

### T15 — 啟動前置檢查

```
preflight(環境) -> 通過 | 失敗(原因)
```

| 驗證的行為 |
|---|
| 來源 repo 掛載不存在 → 失敗，原因指名該路徑 |
| 掛載是**空目錄** → 初始化為 git repo 並繼續，訊息帶解析後的絕對路徑 |
| 空目錄初始化時**一併種下最小 `config-list.toml`**，內容 `load()` 解析得過 |
| 掛載**非空但沒有 `.git`** → 失敗，原因說明目錄非空且未納入版本控制 |
| 掛載有 `.git` 但不是有效 git repo → 失敗，原因明確 |
| repo 已存在但清單檔不見 → 失敗，原因指名該路徑 |
| 清單檔存在但無法解析 → 失敗，指出解析錯誤 |
| **清單檔中某條目引用的來源內容在 repo 中不存在 → 失敗，原因指名該 uid 與路徑**（承接原 T1 的來源存在性；僅查來源側，目標未部署是合法狀態，不得因此失敗） |
| 白名單設定檔缺失或無法解析 → 失敗，原因明確 |
| 全部就緒 → 通過 |
| **失敗時以非零碼結束，不啟動服務** |

對應不變式 2：契約在做實事之前先自我驗證。

**空與非空要分開，因為它們是不同的狀況（#69）。** 空目錄是首次啟動的合法狀態：
volume 掛上了，還沒有人初始化過它。非空卻沒有 `.git` 則不是首次啟動——那裡有沒人審過的
檔案，而 `io/git.record` 的第一步是 `git add -A`，自動初始化等於把它們默默收編進第一次提交。
掛錯路徑會因此看起來像啟動成功。

「掛錯到一個**空**目錄」從容器內部與真正的首次啟動無法區分，這是事實。處置是把**解析後的
絕對路徑**印出來，讓看到訊息的人自己認得出來——訊息可行動，而不是假裝分得出來。

**首次初始化要種下最小清單檔，否則全新安裝開不起來（#66）。** `compose.yaml` 的
`config_repo` 是具名 volume，第一次 `up` 時是空的：初始化成 git repo 之後那裡沒有
`config-list.toml`，而「清單檔不存在 → 失敗」會讓 backend 起不來。一個什麼都還沒納管的
系統，清單應該是**空的**，不是**開不起來**。所以「repo 剛初始化」與「清單檔不見了」
也是兩種狀況：前者種下，後者失敗。

種在 entrypoint 而非 preflight——preflight 是檢查，種檔案是寫入。代價是 entrypoint 會
複述一次 TOML 的形狀，但那個重複不會靜默走鐘：同一次啟動接著就跑 preflight，
`load()` 會當場拒絕一個不合法的種子檔。

### T20 — 內容雜湊

```
digest(path) -> 內容雜湊 | None（檔案不存在）| 具名例外（存在但讀不出來）
```

| 驗證的行為 |
|---|
| 檔案存在 → 回傳其內容的 sha256 十六進位字串 |
| 檔案不存在 → 回傳 `None`，**不丟例外**（未部署是合法狀態，不是錯誤） |
| 內容相同的兩個檔案 → 相同雜湊 |
| **只差一個位元組（結尾換行）→ 不同雜湊** |
| 路徑存在但讀不出來（是目錄、無讀取權限）→ **具名例外**，不可回 `None` |

T2 刻意不讀檔，雜湊由呼叫者算好傳入。這裡就是那個呼叫者所需的那一半，
`decide(target_hash is not None, target_hash, source_hash)` 把兩者接起來。

**比對原始位元組，不是解析後的資料。** 設計文件 §5.4：任何不一致必然代表有人繞過介面
直接修改了目標。比對解析後的資料會讓「語意相同、格式不同」看起來一致——而那正是有人
手改過的痕跡。所以連空白與換行的差異都算偏離。

**「不存在」與「讀不出來」必須分開。** 兩者都回 `None` 的話，一個權限壞掉的目標會被
判成「未部署」，然後 UI 提供一鍵寫出——一個修不好真正問題的動作，而操作者不會知道
為什麼（不變式 2）。

**期望值來自獨立實作。** 測試裡的雜湊字面量以 coreutils 的 `sha256sum` 取得，不是用
`hashlib` 再算一次——用實作自己的算法產生期望值的測試恆真（TEST-PLAN 撰寫規則）。

### T21 — 差異掃描

```
scan(repo) -> [(條目, 狀態)]
```

| 驗證的行為 |
|---|
| 目標不存在 → 該筆為未部署 |
| 目標內容與來源相同 → 一致 |
| 目標內容與來源不同 → 偏離 |
| 多筆條目各自獨立判定，順序與清單檔一致 |
| 空清單 → 空結果，不是例外 |
| **來源內容在掃描時不見了 → 具名例外，指名該條目**（啟動時 T15 驗過，此時消失代表有人動了 repo） |

把 T15（讀清單）、T20（算雜湊）、T2（判定）接起來的那一層。**它有自己的測試介面，
是因為「接起來」本身會出錯**——順序接反、把來源當目標、把 `None` 當成一致——
而那三個介面各自全綠都擋不住這類錯誤。

**放在 io 層而不是 api**：它讀檔案系統，且 CLI 與 HTTP 端點都要用它（ADR-00000009：
兩者走同一組端點，而端點走同一支掃描）。`api/routes` 只做形狀轉換。

**為何不讓 api 自己組合**：那會把這段邏輯的唯一測試位置推到 T9，而 T9 的規格只能在
`docker build` 階段跑。一個要反覆迭代的判定邏輯，測試迴圈不該是「重建映像」。

## 介面層

### T9 — HTTP 端點

走真實 HTTP 對一個真的在跑的服務測。

**規格放在 `test/pytest/system/test_api.py`，同一份檔案在兩個地方執行**（#116、#97）：

| 執行者 | 服務起在哪 | 拿到的是什麼 |
|---|---|---|
| `script/test.sh` | 工具映像裡就地起（`uvicorn` 起在 loopback） | **由 pytest 執行**，`api/` 因此進得了覆蓋率工具的視野 |
| `docker build --target runtime-test` | **建好的映像**裡已經起好的那個 | **保真度**——那才是會被部署的東西 |

**「進得了視野」不等於「有數字」。** 覆蓋率的 `source` 目前只有 `core/`
（`pyproject.toml`），所以 `api/` 仍然不出現在報告裡。搬過來解掉的是「規格不由
pytest 執行」這個結構障礙，量測範圍是另一件工作——見「已知的量測缺口」。

`CM_SYSTEM_BASE_URL` 決定走哪一種：設了就對它測，沒設就自己起一個。**兩者跑同一個
檔案，所以不會分歧**；各自補上對方拿不到的東西。只在其中一種環境會壞的缺陷，正是
跑兩次才抓得到而跑一次抓不到的。

**先前放在 `test/bats/runtime/`，那是錯的兩次。** 一是 `runtime` 不是層級——設計
§3.6.1 軸 2 只有 unit／integration／system／acceptance，而這些規格斷言的範圍是
「整個建好的映像，端到端」，那就是 System。二是它們測的是 Python，依「測試工具對應
被測的語言」該用 pytest；放在 bats 的代價是 `api/routes.py` 與 `api/cli.py` 的覆蓋率
長期是 0%——**不是沒測，是測它們的規格不由 pytest 執行**（#97）。

當初放進 `test/bats/runtime/` 的那個理由（`test.sh` 在工具映像裡跑，那裡沒有 docker
socket 也沒有 docker CLI，起不了被測的容器）**至今仍然成立**——它解釋的是為什麼
`runtime-test` 那一次不可少，不是為什麼要新造一個層級名稱。兩件事分開之後，兩邊都拿得到。

**這一層測不到 compose 的接線**：volume 掛載點、`CM_CONFIG_REPO` 與掛載是否一致、
host networking。那半邊由 compose 自己的規格負責（#90）。**兩邊都要有才算蓋住 T9**，
缺一邊就有一整類問題沒有人擋。

端點集合由設計文件 §3.5.3 的表決定，不在實作時發明。

| 驗證的行為 |
|---|
| 每個端點的正常路徑回傳預期結構 |
| 驗證失敗 → 結構化錯誤（檔案、行號、欄位、建議），**不是純字串** |
| 進版端點：驗證失敗時**不產生變更紀錄也不寫出**（原子性） |
| **進版寫出 N 份、第 k 份失敗 → 前 k-1 份已寫出的目標檔案還原為進版前內容、全部已產生的變更紀錄一併撤銷**，容器內最終狀態與進版前逐位元組相同（承接 T18 移出的批次原子性） |
| 第二個編輯階段被拒，回覆含持有者姓名、email、開始時間 |
| 部署模式下逾時後階段自動釋放 |

### T10 — CLI

CLI 是 HTTP 端點的 client（ADR-00000009），**其測試不重複驗證業務邏輯**。

| 驗證的行為 |
|---|
| 每個指令映射到正確的端點與參數 |
| 端點回錯誤時，CLI 以非零碼結束並印出可讀訊息 |
| 服務未啟動時，訊息明確指出服務未啟動（而非連線錯誤堆疊） |

**規格與 T9 同放 `test/pytest/system/test_api.py`**，理由相同：CLI 要對著一個真的在跑的
服務測。同一份規格檔裡，CLI 那幾則排在 HTTP 那幾則之後，用的是前面寫進 config-repo 的
同一批資料——**兩邊看到同一件事，正是 ADR-00000009 要保證的東西**。

**把關的不是輸出比對，是 `--api`。** CLI 若改成自己讀清單檔，比對輸出的斷言仍會綠；
但讀檔的實作根本不會用到 `--api` 指向的那個 HTTP 位址。斷言那個位址，才是斷言它
真的走了端點。

### T11 — 瀏覽器端到端行為

以自動化瀏覽器操作真實的前後端，驗證**使用者看得到的行為**。

| 驗證的行為 |
|---|
| 輸入身分後可看到清單，各項狀態正確 |
| 納管一個檔案後，它出現在左側樹且狀態為一致 |
| 修改一個參數並儲存 → **存為草稿**；樹上出現草稿標記，目標檔案尚未改變 |
| 再改另一份並儲存 → 兩份草稿並存，進版按鈕顯示「進版 (2)」 |
| 按下進版 → **兩份一起送出**，各產生一筆變更紀錄；目標檔案改變 |
| 輸入非法值 → 該列標示錯誤，**儲存按鈕停用**；int 欄輸入小數被拒 |
| **double 型別參數存後，其值帶小數點**（`5` → `5.0`）——擋 ROS 型別錯誤的招牌行為 |
| 外部修改目標檔案後按「檢查差異」→ 該項顯示偏離，可進入差異檢視 |
| 偏離時選「以來源覆蓋」→ 目標內容還原，狀態回到一致 |
| 偏離時選「將目標現況納入來源」→ 來源更新且產生紀錄；**若目標內容違反驗證則被拒** |
| 偏離時選「**先納入、待修正**」→ 目標現況載入草稿；**若含非法值，橫幅與該列即時警告（原因＋正確寫法），進版按鈕停用**，改乾淨後可進版 |
| 退版後參數回到先前值 |
| 開第二個分頁 → 顯示唯讀，並指出持有者 |
| 部署模式閒置逾時 → 自動退出且階段釋放 |
| **一般使用者模式下，型別欄為純文字**、白名單與屬性編輯入口**不顯示**（非停用） |
| 切換為開發者後，上述元素出現 |
| 搜尋範圍下拉選「參數名稱」後，只命中參數名稱 |
| 修改群組並儲存 → 左側樹立即重建 |
| list 參數可新增、移除、**以 ↑↓ 調整順序**，順序變更後儲存生效 |
| 歷史列表**不出現 `cfg`／`revert`／`import` 等內部代號** |
| 型別指定後該列顯示「已指定」，清除後回到推斷值 |
| **有未進版草稿時退出 → 二次確認並說明草稿將遺失** |
| 身分輸入頁的角色切換明顯可見（不在選單內） |

**測的是行為，不是 DOM。** 選取元素以語意屬性為準，詳見 `doc/UI-ELEMENTS.md`。

## 驗收層

系統層問「這個功能運作正確嗎」，驗收層問「**使用者能達成他的目的嗎**」。

差別具體在哪：系統層的每一步都通過，但**步驟順序讓人卡住**時，系統層測不出來。

### A1 — 把一份新 config 納入管理

| 旅程步驟 | 通過條件 |
|---|---|
| 開啟系統、輸入身分 | 不需要密碼或事先設定 |
| 找到那份檔案 | 從介面就能瀏覽檔案系統，不需先知道完整路徑 |
| 路徑不在白名單 → 被拒 | **錯誤訊息直接提供加入白名單的入口**（開發者）或說明需聯繫誰（一般使用者） |
| 檔案含歧義寫法 | 列出清單並要求確認，**不阻擋匯入** |
| 完成 | 該項目出現在左側樹、狀態為一致、**原始檔案內容未被改動** |

**失敗判準**：任一步需要離開介面（改設定檔、下指令、問人）即為不通過。

### A2 — 調整參數並進版

| 旅程步驟 | 通過條件 |
|---|---|
| 找到那個參數 | 搜尋參數名稱即可定位，不需先知道它在哪個檔案 |
| 修改 | **以輸入框修改，不需要知道 YAML 語法** |
| 輸入超出範圍的值 | 該列即時標示，儲存按鈕停用 |
| 改回合法值並儲存 | **存為草稿**；樹上出現草稿標記，目標檔案尚未改變 |
| 再改另一份 config 並儲存 | 兩份草稿並存 |
| 按下進版 | **兩份一起送出**，各產生一筆紀錄；註解未遺失 |
| 確認改了什麼 | 歷史中可見改了哪個參數、從什麼變成什麼、誰改的 |

### A3 — 發現並處置一次偏離

| 旅程步驟 | 通過條件 |
|---|---|
| 開啟系統 | **不需主動掃描即看到警示** |
| 理解發生什麼 | 橫幅說明該修改未經介面進行、沒有作者資訊 |
| 判斷 | 並排比對看得出改了哪些參數 |
| 處置 | 三個選項（以來源覆蓋／將現況納入來源／先納入待修正）的後果在按下之前就說明清楚 |
| 現況含非法值 | 「將現況納入來源」被擋並說明原因；改走「先納入、待修正」把現況載入草稿修正，**壞內容不進來源、也不靜默丟棄**（新增出口，2026-09-04） |
| 完成 | 狀態回到一致，且**處置本身留下紀錄** |

### A4 — 出錯後能自行修正

| 情境 | 通過條件 |
|---|---|
| 布林值寫成 `no` | 訊息指出行號、說明為何不接受、**給出正確寫法** |
| 重複的參數名稱 | 訊息列出**所有**出現位置 |
| 跨欄位規則違反 | 說明是哪兩個欄位衝突；可 override 但需填理由 |
| 通用 | **沒有任何錯誤訊息只說「格式錯誤」或「操作失敗」** |

**失敗判準**：使用者看完訊息後仍不知道下一步該做什麼。

### A6 — 開發者整理一份新納管的 config

| 旅程步驟 | 通過條件 |
|---|---|
| 切換為開發者 | 身分輸入頁上的切換明顯可見，不需尋找 |
| 找到那份 config | 它在「未分群」節點下，**不需要記得它叫什麼** |
| 設定群組 | 儲存後左側樹立即重建 |
| 更正型別 | 型別欄可改；改完標示為「已指定」 |
| 發現改錯了 | **可個別清除該欄位的指定**，不影響其他欄位 |
| 切回一般使用者 | 型別欄變回純文字，屬性編輯入口消失 |

**失敗判準**：任何開發者專屬功能在一般使用者模式下**顯示但停用**。

### A5 — 未受訓者可自行操作（人工）

**無法自動化。** 由未參與開發的同事在無人指導下，依序完成 A1 至 A4；
由另一位開發者完成 A6。全程不得詢問操作方式。

這是 v0.9.0 的驗收條件。前四項可腳本化，這一項不行——**能不能自己摸索出來，
只能由真的沒摸索過的人來測**。

## 工具層（repo 自身的守門腳本）

### T19 — 守門腳本的規則

**介面**：每支守門腳本的命令列。餵一個目錄、一個 base ref，或一組受控的
`PATH` 與環境變數進去，觀察**結束碼與訊息**，不碰腳本內部。規格以 bats 撰寫，
放在 `test/bats/unit/<腳本名>.bats`。

| 腳本 | 規格 |
|---|---|
| `script/lint_adr.sh` | `test/bats/unit/lint_adr.bats` |
| `script/lint_commit.sh` | `test/bats/unit/lint_commit.bats` |
| `script/lint_paths.sh` | `test/bats/unit/lint_paths.bats` |
| `script/lint_portability.sh` | `test/bats/unit/lint_portability.bats` |
| `script/lint_messages.sh` | `test/bats/unit/lint_messages.bats` |
| `script/check_file.sh` | `test/bats/unit/check_file.bats` |
| `script/test.sh` | `test/bats/unit/test.bats` |
| `script/lint_checkpoints.sh` | `test/bats/unit/lint_checkpoints.bats` |

**`script/test.sh` 被觀察的不是 lint 規則，而是「缺工具不得靜默通過」**（#72）。
它與四支 lint 同屬一個測試介面，因為觀察位置相同：命令列進去，結束碼與訊息出來。
差別只在輸入多了一項——它以 `command -v` 判定工具在不在，所以「拿掉一支工具」
只能靠**重建 `PATH`**，覆寫不掉。被觀察的行為：

| 行為 | 通過條件 |
|---|---|
| 缺一支檢查工具 | 非零結束，訊息指名該工具與安裝方式 |
| 缺多支 | **一次列出全部**，且只列缺的那些 |
| `CM_LINT_ALLOW_MISSING=1` | **結束碼 0**，且訊息指名哪幾項沒跑 |
| 缺席的工具 | 不被呼叫（不是「呼叫了才發現不在」的 127） |
| `CM_IN_TEST_IMAGE=1` ／ `CM_TEST_LOCAL=1` | 就地執行，不轉進容器 |
| 兩者皆無 | 轉進容器；docker 缺席時訊息指出逃生口 |
| 一條規格自己跳過 | 結束前被**逐條指名**，不混在一片 ok 裡 |
| 一個層級一條規格都沒有 | 被指名；`--level` 不以 pytest 的 5 結束（那是假紅燈） |

**後兩條與前六條是同一個保證的兩半。** 前面擋的是「工具不在卻回報通過」，後面擋的是
「規格在卻沒有執行」——兩者在輸出上與全綠的差別都只有幾行字。兩種沉默都不算失敗
（那些規格在工具映像裡確實跑不了，那一層確實還沒有規格），但兩種都不准安靜：
降級要大聲，與 `CM_LINT_ALLOW_MISSING` 是同一個先例。

**`lint_checkpoints.sh` 不由 `script/test.sh` 執行，是 CI 的一個獨立 job。**
它需要 GitHub API 讀被引用的 issue，而 `test.sh` 在容器裡跑、那裡沒有 token。規格以
PATH 上的假 `gh` 替換，所以規格本身不需要網路，也不會因為某張真的 issue 被改動而轉紅。

**帳本記 commit 主旨，不記 SHA。** SHA 不是穩定識別碼：rebase 改寫它、squash 合併
讓它從歷史裡消失，而這個 repo 規定推送前 rebase、要求分支與 base 同步、合併一律
squash——每個 PR 都必然經歷至少一次 SHA 改寫。第一版綁在 SHA 上，實際效果是每次
合併前手動重填一輪帳本，而那個手動步驟沒有東西擋著它被填錯（#129，實測兩次）。

**它擋不住的那一件事**：工具只能確認「有一筆真的存在的 commit 被記在那一行」，
**不能確認那筆 commit 真的實作了那條驗收條件**。那需要人看。寫在這裡，免得日後
以為它被驗過了。

**每條規則都要有一個會觸發它的案例。** 一支所有 FAIL 路徑都沒被執行過的 lint，
它擋得住什麼是沒有證據的——規則看起來在運作，而那正是回歸風險最高的形狀。
`shellcheck` 不能充數：依 `doc/test/TEST.md` 那是軸 1 靜態分析，不是動態測試。

**WARN 的案例要斷言結束碼為 0。** fail 與 warn 的差別就是擋不擋得住合併，
只斷言「訊息裡有 WARN」不會發現一條被誤寫成 fail 的 warn。

**規格必須通得過突變檢查。** 把它針對的規則從腳本裡拿掉，該規格要轉紅。
不會因規則消失而轉紅的規格，測的不是那條規則。這一項不自動化，
在 PR 描述裡記下做過哪些突變與結果。

**`script/check_file.sh` 是提前的回饋，不是閘門。** 它只跑「一個檔案就判定得了」的
檢查（ruff、`lint_messages`、shellcheck），CI 才是權威。它仍然有規格，因為它的失敗
形狀跟閘門一樣危險：一個接錯線的單檔檢查什麼都不跑，而它每次都回 0——看起來與
「檢查過了、乾淨」完全一樣。

其餘 21 支 shell 腳本（五支容器 wrapper、`hooks/dispatch.sh`、14 支 hook、`local/cfg/cfg.sh`）
在 #74 逐支盤點後**轉為刻意的空格**，理由記在「覆蓋率審計」的該節，不再列為待辦。

### 已知未涵蓋：§0.4「例外處理的具體要求」

設計 §0.4：「所有規範必須可由工具檢查——**無法自動檢查的規範等同不存在**。」
三條要求裡只有第 2 條有專屬工具，另外兩條的狀態逐條記在這裡。
**寫下理由是「刻意留空」與「漏掉」的唯一差別。**

| §0.4 要求 | 檢查工具 | 狀態 |
|---|---|---|
| 1. 不得捕捉後僅 `pass` 或僅 `log.debug` | `E722`／`BLE001`（＋ pylint 同名檢查） | **部分涵蓋**（#112） |
| 2. 錯誤訊息須含三要素 | `script/lint_messages.sh` | 已涵蓋 |
| 3. 不得將驗證失敗轉為警告後繼續 | 無 | **未涵蓋**，理由見下 |

第 1 條的涵蓋邊界來自實測——在檢查映像裡逐個形狀跑過 ruff 與 pylint，不是憑印象：

| 寫法 | 被誰擋下 |
|---|---|
| `except:`（不論 handler 內容） | `E722` ＋ pylint `bare-except` |
| `except Exception:` ／ `BaseException:`（不論內容） | `BLE001` ＋ pylint `broad-exception-caught` |
| `except ValueError: pass`（單一 handler） | 只有 `SIM105` |
| `except ValueError: log.debug(...)` | **無** |
| `contextlib.suppress(ValueError)` | **無** |
| 兩個 handler，兩個都 `pass` | **無** |

`SIM105` 不算這條規範的執行者：它的修法是改寫成 `contextlib.suppress(...)`——同一個
吞錯誤，換一個拼法，而改寫之後就再也沒有工具看得到它。把它當成「第 1 條有在檢查」，
正是這個 repo 抓過七次的那個形狀。

所以 §0.4 第 1 條**指名的那個形狀**（捕捉具名例外之後只 `pass` 或只 `log.debug`）
目前沒有任何工具擋得住。**這一條不是「難以自動化」**：語法形狀清楚，一次 AST 走訪
就判得出來。它是**還沒做**，記在 #112。真正做不到的是同一條的後半句「捕捉即代表有
處理策略」——handler 裡有東西不代表那是策略——那半句留給 code review，刻意如此。

**第 3 條未涵蓋，理由是它判的不是語法而是層級意圖。** 同一段「記下警告然後繼續」的
程式碼，在第 3 層是設計（不變式 4 明列「第 3 層可 override，需填理由」），在第 1、2 層
是違規。工具讀不出某個 `warnings.append` 屬於哪一層——驗證層級是設計上的分層，不是
程式碼裡的一個欄位。等 `core/validate`（T3、#16）落地、層級在資料模型上具名之後，
這一條才可能變成「第 1、2 層的處置不得寫進 warnings」這種檢查得了的形式。在那之前
它是刻意留空。

### 刻意的空格

**刻意留空與漏掉的差別在於有沒有寫下理由。** 沒有理由的空格就是漏掉。
因此本節不寫「無需測試」這種結論，每一列都寫出**行為在哪裡被觀察**，
或**為什麼那裡沒有行為可觀察**；有代價的，代價也寫出來。

| 沒有測試介面的東西 | 為何可以沒有 |
|---|---|
| `core/models` | 資料模型是宣告，本身無行為。其約束在 T1 載入時被驗證，兩個有行為的衍生屬性 `ConfigList.warnings` 與 `FileEntry.ref` 也在 T1 被觀察——後者以完整形式 `<name>@<hostname>-<uid>` 斷言，不是拆成子字串 |
| 模式判定（開發／部署） | 讀設定回傳一個列舉值，無邏輯可測。其**效果**在 T13 與 T11 被驗證 |
| 三層驗證的「層」本身 | 層是組織方式不是行為。各層的實際檢查在 T3 逐項驗證 |
| 「未納管」的判定 | 定義即「不在清單檔中」，由清單成員查詢直接得出、無分支邏輯可測。其**效果**在 T14（解除納管後移除）與 T11 被觀察 |
| 四支 `__init__.py` | 套件標記。三支只有 docstring，`core/` 那支是空檔案——沒有任何可執行的行為。它們該不該存在由 ADR-00000026 決定，而那條決定的證據是「直譯器起得來」，每一次執行都在驗它 |
| `script/{build,run,exec,stop,prune}.sh` | 薄 wrapper：行為即把參數轉給 `docker compose`。它們是**開發者的操作工具，不是交付物**，且不在任何 CI 路徑上——CI 直接 `docker build --target runtime-test`，不經過 `build.sh`。失效在下一次手動使用時立刻可見，且動不到來源 repo 或目標檔案。**代價**：`--stage`／`--all`／未知參數這幾條解析路徑因此沒有證據 |
| `script/hooks/dispatch.sh` | 七行、一個函式，且 ADR-00000023 已決定模板導入時整支被取代——為一個即將被丟掉的實作寫規格，測到的是實作而不是行為。**代價寫明**：「pre-hook 失敗必須中止操作」這條屬於不變式 2 的保證目前沒有證據，**導入模板時必須重新確認**，因為那正是它靜默失效不會被發現的時刻 |
| `script/hooks/pre/run.sh` | 它檢查的是**主機**上的掛載點在不在，而本專案所有檢查都在容器內跑（ADR-00000027）。容器裡沒有那個主機目錄可以觀察——要測它就得替「主機不是這個專案的證據」開一個例外，那個代價比這支七行守衛的風險大 |
| `script/hooks/post/build.sh` | 行為即觸發 `runtime-test` 階段的建置。**那個階段本身就是被觀察的位置**：smoke（`test/bats/system/entrypoint_smoke.bats`）與 T9／T10（`test/pytest/system/test_api.py`）都在它建置時執行，CI 的 build job 也直接建同一個階段 |
| 其餘 12 支 `script/hooks/{pre,post}/*.sh` | 刻意的空殼（ADR-00000023）：檔案裡只有說明契約的註解，沒有可執行的行為。**空檔案沒有行為可觀察**；它們該不該存在、以及哪幾支永遠不會被呼叫，由 ADR-00000023 記錄並寫在各自的檔案裡，不由測試決定 |
| `script/local/cfg/cfg.sh` | 行為即把 `just cfg <verb>` 轉給 `python -m config_manager.api.cli`。被轉呼叫的那一端落在 T10 |

### 已知的量測缺口：覆蓋率與型別檢查都只看 core

上面兩張表講的是「行為有沒有被觀察」。這一節講的是另一件事：**自動化的量測本身涵蓋到哪裡。**
兩者不同，而把它們混為一談會讓「有整合測試」被誤讀成「有數字在守」。

現況（`pyproject.toml`，不是這份文件；閾值寫在能被檢查的地方）：

| 量測 | 設定 | 範圍 |
|---|---|---|
| 覆蓋率 | `[tool.coverage.run] source = ["src/config_manager/core"]`，`fail_under = 85` | 只有 `core/` |
| 型別 | `[tool.mypy] files = ["src/config_manager"]`，`strict = true` | `core`／`io`／`api`（#97 起） |

**影響：`io/` 與 `api/` 兩者皆無。** `io/writer`、`io/git`、`io/preflight`、`io/digest`、
`io/scan` 確實各有整合層規格（T8／T7／T15／T20／T21），`api/routes` 有 T9、`api/cli` 有 T10
——但**沒有任何數字會在它們新增的分支沒被執行時轉紅**。型別那一半已經補上（#97）：
`--strict` 現在涵蓋整個 `src/config_manager/`，逐檔清乾淨後零錯誤，並以突變檢查確認過
它真的在看那兩層（`io/scan.py` 一個未標註的函式、`api/routes.py` 一個回傳型別不符，各自被擋下）。

**`web/` 更徹底：連規格都沒有。** T11 沒有執行通路，頁面裡的 `data-testid` 是給未來的測試
準備的，沒有測試在用它們。這與上面兩層是不同的缺口——那兩層是「有規格、沒數字」，這一層是
「兩者皆無」。追蹤於 #99，理由同樣是「還沒做」而不是「不用做」。

**為什麼這裡只記錄、不順手修。** 把 `io/` 與 `api/` 加進 coverage 的 `source`，85 的下限會
立刻落在一組覆蓋率遠低於 `core/` 的模組上，門檻在一個與本次審計無關的地方爆掉；為了讓它過而
把下限調低，等於連 `core/` 的保證一起調弱——**一個門檻同時守兩個標準不同的區域，結果是守住
比較鬆的那個。** mypy 那一半在 #97 做掉了：加進 `files` 之後實測**零錯誤**——「後面跟著一批要逐檔處理的
`--strict` 錯誤」是當時的推測，不是量出來的。

**要修的話怎麼修**：兩件事分開，各自一個 issue，各自把數字釘在它守得住的地方——覆蓋率用
per-module 的下限（讓 `core/` 維持 85，`io/`／`api/` 各自訂一個現況擋得住、之後只能往上調的值），
mypy 先把 `io/` 與 `api/` 納入 `files` 再逐檔清乾淨。追蹤於 #97。

**這一節記的是 #97 之前的現況**，兩件事的實際結果見該 issue 與其 PR：per-module 下限那個
建議被作廢，改成四個資料夾同一條線 85、分開計算分開擋。

## 撰寫規則

- **紅燈先行。** 先寫會失敗的測試，再寫剛好讓它通過的程式碼。
- **一次一片。** 一個測試介面、一個測試、一個最小實作。
- **垂直切片，不橫向切片。** 不先寫完全部測試再實作。
- **重構不在迴圈裡。** 它屬於 review 階段。
- **期望值必須來自獨立來源**，不可用與實作相同的方式重算。
- **一個測試一個邏輯斷言。**
- **測試名稱描述「做得到什麼」而非「怎麼做」**，並使用 `CONTEXT.md` 的用語。

## 與版本里程碑的關係

版本驗收檢查點是**結果**，本文件的測試介面是**觀察位置**。

一個版本的實作是**多輪垂直切片**，直到該版本的驗收檢查點通過。
**不是「先寫完該版本的所有測試再實作」**，那正是橫向切片的反模式。
