# 測試項目定義

> **狀態：2026-09-04 逐項確認並修訂。**
> 已確認核心層七項介面，並套用四項核心修正（T1／T2／T4／T18）、將兩項檢查改置 IO 層
> （來源存在性 → T15、符號連結逃逸 → T8）、補 T9 批次回滾與 T6／T7 行為，且新增偏離
> 處置的「先納入、待修正」出口（A3／T11／T18）。
> 測試先行的規則是「**沒有經過確認的測試介面，不寫測試**」。已確認者進入 red → green 迴圈。

用語依 `CONTEXT.md`，測試名稱也應使用同一套詞彙。

---

## 什麼是「測試介面」

**測試介面**是「從哪個位置觀察行為」。同一段程式碼可以從很多位置觀察，
但只有公開介面這個位置是穩定的。

| 觀察位置 | 測試長什麼樣 | 好壞 |
|---|---|---|
| 內部實作 | 「有沒有呼叫 `chmod`？」「暫存檔名對不對？」 | **壞**。改寫實作就壞，但行為沒變 |
| 公開介面 | 「呼叫 `write()` 之後，目標檔案的內容與權限對不對？」 | **好**。內部怎麼改都不影響 |

**測不了全部**，所以事先議定測試介面，是讓測試力氣落在關鍵路徑與複雜邏輯上、
而不是散在每個邊界案例上的方法。

編號 `T1`–`T18` 為單元／整合／系統層，`A1`–`A6` 為驗收層。

## 核心層（純邏輯，無 I/O，可在無檔案系統／無 git 下執行）

### T1 — 清單檔載入與寫回

```
load(text) -> ConfigList | 具名例外
dump(ConfigList, 原樣資訊) -> text
```

| 驗證的行為 | 為何在這裡測 |
|---|---|
| 合法清單檔可載入，欄位值正確 | 基本契約 |
| uid 重複 → 具名例外，訊息指出是哪兩筆 | 不變式 2 |
| 目標路徑重複 → 具名例外（寫出順序決定結果，是靜默 bug） | 不變式 2 |
| 目標含 `..` → 具名例外 | 逃逸防護 |
| format 非允許值 → 具名例外 | — |
| **無法辨識的欄位 → 具名例外，指出欄位與行號**（含 `warnings` 等內部欄位，防止由清單檔注入） | 不變式 2 ／ PDF §329（2026-09-04 檢討新增） |
| `(name, hostname)` 重複 → **警示而非例外**（uid 已保證唯一） | 警示與錯誤的分界 |
| **寫回未改動的清單檔，輸出與輸入逐位元組相同** | 清單檔本身也要原樣保留 |
| 新增一筆條目後寫回，**既有條目的註解、順序、引號樣式不變** | 同上 |
| **附加的新條目帶選填欄位（schema／requires_privilege／permissions）時，寫回後全數保留** | 不變式 2（PDF §4.3 選填欄位表；靜默丟欄位即靜默失敗） |
| **改動或移除既有條目後寫回 → 具名例外**（dump 目前只支援未改動與新增；靜默丟失改為大聲失敗，待 T6 式 round-trip 把手實作編輯／移除） | 不變式 2（2026-09-04 檢討新增） |

**不測**：TOML 語法本身（那是 parser 的責任）。

**為何 dump 在這裡而不在 T6**：T6 處理的是**被管理的 config**（四種格式），
T1 處理的是**清單檔本身**（固定為 TOML）。兩者的原樣保證各自獨立，混在一起會
使「哪個壞了」難以定位。

**T1 的「原樣資訊」是原始清單檔文字**：dump 以 tomlkit 重新解析後在其上套用變更
（與 T6 的 parse 回 `(資料, 原樣資訊)` tuple 形狀不同，但各自自洽）。

**來源檔案存在性移至 T15**：核心無 I/O，`load(text)` 不讀磁碟；「清單裡每筆來源檔
是否存在」改由啟動前置檢查逐筆驗證。

### T2 — 狀態判定

```
decide(target_exists, target_hash, source_hash) -> 一致 | 偏離 | 未部署
```

| 驗證的行為 |
|---|
| 目標不存在 → 未部署 |
| 雜湊相同 → 一致 |
| 雜湊不同 → 偏離 |
| 三種狀態的判定順序（先存在性、後內容） |

**這個測試介面刻意不讀檔**——雜湊由呼叫者算好傳入。因此它的測試完全不需要檔案系統，
這是核心層可測性的關鍵設計（ADR-00000011）。

**「未納管」不由此判定**：其定義是「不在清單檔中」（CONTEXT），在呼叫 decide 之前就由
清單成員查詢決定，故 decide 只回三種狀態。

**decide 不收 entry**：判定只依存在性與雜湊，entry 用不到；實作時移除以免未使用參數。

### T3 — 驗證

```
check(content, format, rules, schema?) -> [問題]   # 空清單 = 通過
```

| 層 | 驗證的行為 |
|---|---|
| 第 1 層 | `yes`/`no`/`on`/`off` → 問題，指出行號與建議寫法 |
| 第 1 層 | 前導零 `08`、科學記號 `1e3`、`1.10` 尾隨零 → 問題 |
| 第 1 層 | Tab 縮排、尾隨空白 → 問題，指出行號 |
| 第 1 層 | 重複 key → 問題，**列出該 key 的所有出現行號** |
| 第 2 層 | 型別不符 schema → 問題，指出欄位 |
| 第 2 層 | 超出數值範圍 → 問題 |
| 第 2 層 | **人工指定的型別優先於推斷型別** |
| 第 2 層 | **同一份 schema 驗 YAML / TOML / JSON 三種格式的等價內容，結果一致** |
| 第 3 層 | 跨欄位規則違反 → 警示（非錯誤），可 override |
| — | 合法內容 → 空清單 |

**每個問題都必須含檔案、行號／欄位、修正建議三要素**——這本身是被測的行為。

**不測**：底層 schema 函式庫的驗證邏輯。

### T4 — 白名單判定

```
decide(rules, path) -> 允許 | 拒絕(原因)
```

| 驗證的行為 |
|---|
| 白名單內的路徑 → 允許 |
| 白名單外 → 拒絕，原因指出未涵蓋 |
| `../` 逃逸至白名單外 → 拒絕（正規化後比對） |
| 相對路徑 → 拒絕（要求絕對路徑） |

**符號連結解析移至 T8**：readlink／realpath 是 I/O，核心只做正規化後的字面比對；
連結是否逃逸白名單在寫出時點（T8）以 realpath 解析後判定。

### T5 — 身分推導

```
derive_name(target_path) -> name
new_uid(now, previous=None) -> uid
```

| 驗證的行為 |
|---|
| `/opt/robot/navigation/params.yaml` → `navigation-params` |
| `/etc/docker/daemon.json` → `docker-daemon` |
| 底線轉連字號、去副檔名、去重疊層級 |
| uid 由匯入時刻的毫秒時間戳轉 base36 產生，長度 8 碼 |
| uid 的**值**由注入的時刻決定——期望值手算寫死，不用實作的算法重算 |
| 兩次連續呼叫產生的 uid **嚴格遞增**（可排序 = 保留納管順序） |
| 同一毫秒內的兩次呼叫不會得到相同值（後者遞增 1） |

**唯一性來自時間單調遞增，不是機率。** backend 是唯一寫入者，因此不存在競爭。
T1 的重複檢查保留，但角色是**防呆**，不是主要保證機制。

**new_uid 收前一個 uid**：同一毫秒內遞增 1 需要知道前值，而純函式不藏狀態
（ADR-00000011），故把前值當參數傳入（`previous`，預設 None ＝ 首次）。

不寫「連續產生 N 次無重複」這類斷言——那是機率性測試，會偶發失敗而程式碼完全正確。
**偶發失敗的測試比沒有測試更糟**：它訓練人忽略紅燈。

### T12 — 型別推斷與人工指定

```
infer_types(資料) -> {欄位路徑: 型別}
draft_schema(型別對照) -> JSON Schema 骨架
```

| 驗證的行為 |
|---|
| 各基本型別正確推斷（整數、浮點、布林、字串、陣列、物件） |
| **浮點與整數區分正確**（`1.0` → 浮點，`1` → 整數）——ROS 型別錯誤的來源 |
| 巢狀結構的欄位路徑正確 |
| 陣列推斷出元素型別；空陣列標示為未知 |
| 產生的骨架可被 schema 驗證器載入，且能驗過原始資料 |
| 人工指定型別後，該欄位的型別以指定為準 |
| **清除指定後，回到推斷值**（不是清成空值） |
| 逐欄位清除，不影響同一份 config 的其他指定 |

**不測**：推斷結果是否「符合作者原意」——那無從得知。人工指定存在的理由正是推斷做不到這件事。

### T13 — 編輯階段生命週期

```
acquire(使用者, now) -> 階段 | 已被占用(持有者資訊)
renew(階段, now) -> 成功 | 已失效
release(階段)
sweep(now) -> [被回收的階段]
```

| 驗證的行為 |
|---|
| 無人持有時可取得 |
| 已被占用 → 拒絕，回覆含持有者姓名、email、開始時間 |
| 持有者釋放後，他人可立即取得 |
| **續期逾時後階段自動回收**，他人可取得 |
| 部署模式：閒置達設定時間後階段被回收 |
| 開發模式：不因閒置回收 |
| 已失效的階段續期 → 明確失敗，不靜默重新取得 |
| **階段逾時釋放時，草稿一併清除**，且回報「有 N 份草稿被清除」而非靜默丟棄 |

**必須注入時鐘。** 這個測試介面的行為全部與時間相關，若讀系統時間，測「10 分鐘後
逾時」就要真的等 10 分鐘。**這是設計要求，不是測試技巧**——讀系統時間的實作無法被有效測試。

### T14 — 參數索引與搜尋

```
index(uid, 資料) -> [(uid, 參數路徑, 值)]
reindex(索引, uid, 資料) -> 索引        # 更新：先移除該 uid 舊項目再重新展平
unindex(索引, uid) -> 索引              # 解除納管：移除該 uid 所有項目
search(索引, 查詢, 範圍) -> [命中]
```

| 驗證的行為 |
|---|
| 巢狀結構展平成正確的參數路徑 |
| 陣列元素以索引納入路徑 |
| 依參數名稱搜尋，命中含 uid 與路徑 |
| 依參數值搜尋 |
| **搜尋範圍為「全部」時，命中為各範圍的聯集** |
| **指定範圍時，其他範圍的命中被排除** |
| **修改一個參數後重新索引，舊值不再命中、新值命中** |
| **解除納管後，該 uid 的所有項目從索引移除** |
| 查無結果回空清單，不是例外 |

最後兩項是索引最容易出錯的地方——**新增容易，移除與更新容易漏**。因此更新與移除各有
獨立函式（`reindex` / `unindex`），而非要呼叫端自己拼——讓「容易漏」的兩件事有明確歸屬。

### T16 — config 屬性與群組

```
update_attributes(uid, {名稱, 群組, 主機, 說明}) -> ConfigList | 具名例外
group_tree(ConfigList) -> 樹狀結構
```

| 驗證的行為 |
|---|
| 修改群組後，**樹結構依新群組重建** |
| 一份 config 屬多個群組時，**在每個群組節點下都出現** |
| 無群組的項目歸入「未分群」節點 |
| 父節點的狀態為子節點中最嚴重者（偏離 > 未部署 > 一致） |
| 修改名稱不影響 uid 與任何關聯 |
| 屬性變更以 `meta` 類型記錄，不與內容變更混在一起 |

### T17 — 角色權限

```
permits(角色, 動作) -> 允許 | 拒絕
```

| 驗證的行為 |
|---|
| 一般使用者：可修改參數值、退版、處置偏離、在既有白名單內納管 |
| 一般使用者：**不可**修改參數型別、維護白名單、編輯 config 屬性 |
| 開發者：上述全部允許 |
| 角色切換後權限立即生效，不需重新輸入身分 |

**角色是自我宣告，不是認證。** 本測試介面驗證的是**權限對照表本身正確**，
不驗證「無法偽造角色」——v0.10.0 前沒有那個保證，也不假裝有。

### T18 — 草稿與進版

```
save_draft(階段, uid, 內容) -> 階段 | 驗證問題
adopt_draft(階段, uid, 目標現況) -> 階段 + [警告]   # 偏離處置的「先納入、待修正」出口
promote(階段) -> [變更紀錄] | 驗證問題(指出哪一份的哪一項)
discard(階段, uid?) -> 階段
```

| 驗證的行為 |
|---|
| 儲存草稿**不產生變更紀錄、不寫到目標位置** |
| 儲存時跑第 1 層驗證，不通過則不存 |
| 多份草稿共存，各自獨立 |
| **進版時任一草稿驗證失敗 → 整批不進版**，錯誤指出是哪一份的哪一個參數 |
| 進版成功 → 每份 config 各產生一筆變更紀錄，且都在同一次操作中 |
| 捨棄變更後，草稿消失且來源與目標皆未改變 |
| 進版後草稿清空 |
| **草稿與四種狀態正交**：一份「一致」的 config 可以同時有草稿 |
| **adopt_draft 把目標現況載入草稿**：內容照載，回傳每個非法值的警告（檔案／欄位／原因／建議三要素），**不因非法而拒載** |
| adopt_draft 與 save_draft 的分界：**save_draft 擋第 1 層、adopt_draft 不擋但警告**——前者是人正在編輯、後者要把壞內容撈進來修 |
| adopt_draft 產生的草稿仍受進版約束：**含非法值時整批不進版**，改乾淨後正常進版，作者記為進版者（偏離內容因此被重新掛到真人身上） |

**不測**：草稿在階段間共享——本系統一次只有一個編輯階段（ADR-00000014）。

**寫出批次回滾移至 T9**：跨多份的原子寫出＋失敗回復牽涉 I/O，核心 `promote` 只產生
`[變更紀錄]` 這批資料並保證「任一驗證失敗整批不進版」；實際寫出與回滾由 T9（系統層、
真實容器）擁有。

## IO 層（adapter，以真實檔案系統與 git 測試）

### T6 — 格式解析與原樣寫回

```
parse(text, format) -> (資料, 原樣資訊) | 解析錯誤(行號)
dump(資料, 原樣資訊) -> text
```

| 驗證的行為 | 為何重要 |
|---|---|
| **parse → dump 未改動任何值時，輸出與輸入逐位元組相同** | 原樣保證的核心 |
| 改動一個值後 dump，**註解、引號樣式、鍵順序、縮排全部保留** | 同上 |
| **新增／刪除一個鍵、或重排 list 元素後 dump，未觸動的兄弟節點其註解、引號、縮排、順序全數保留**，新增／移動的元素以一致樣式渲染 | 結構性編輯的原樣保證（T11／A2 的 list 重排、A6 整理流程依賴） |
| 語法錯誤 → 解析錯誤含行號 | 不變式 2 |
| 四種格式（yaml / json / toml / ini）各自通過上述 | |
| `raw` 格式不解析，原文通過 | |

### T7 — 變更紀錄

```
record(uid, 類型, 說明, 作者) / history(uid, 類型過濾) / revert(uid, 版本)
```

| 驗證的行為 |
|---|
| 記錄後可於歷史中查得，作者正確 |
| 訊息格式為 `<類型>(<uid>): <說明>` |
| 以 `cfg` 過濾時，`revert` 與 `meta` 紀錄不出現 |
| 退版後歷史仍含全部先前紀錄（**未被截斷**） |
| 退版產生新紀錄而非移動指標 |
| **退版至版本 V 後，該 uid 在來源 repo 的內容等於 V 版當時內容**（以 `history()`／既有讀取介面驗證，非 `git log`） |

**測試方式**：對真實的臨時 git repo 操作，透過本測試介面驗證（`history()`），
**不直接跑 `git log` 檢查**——那是繞過介面驗證（反模式）。

### T8 — 原子寫出

```
write(目標路徑, 內容, 權限) -> 成功 | 例外
```

| 驗證的行為 |
|---|
| 寫出後內容正確、owner／group／mode 符合指定 |
| 目標已存在時被覆蓋 |
| **寫入過程中斷 → 目標維持原內容，不出現半殘檔案** |
| **目標路徑（或其父目錄）經 realpath 解析後逃出白名單 → 具名例外，且寫出不發生**；不靜默跟隨或改寫連結所指的檔案 |
| 目標目錄不可寫 → 具名例外（訊息含路徑＋原因＋下一步，不只說「操作失敗」） |

「中斷」以在改名前注入失敗來模擬。

**符號連結逃逸落於此**（原 T4 移入）：寫出是逃逸真正造成危害的時刻（ADR-00000003 警告
改名會把連結替換成一般檔案而靜默失效）。實作二選一：`write` 簽章補收白名單 rules，或在
其前置一個 realpath ＋ T4 守門函式；本測試介面驗證的是「逃逸被拒、寫出未發生」這個結果。

### T15 — 啟動前置檢查

```
preflight(環境) -> 通過 | 失敗(原因)
```

| 驗證的行為 |
|---|
| 來源 repo 掛載不存在 → 失敗，原因指名該路徑 |
| 掛載是**空目錄** → 初始化為 git repo 並繼續，訊息帶解析後的絕對路徑 |
| 掛載**非空但沒有 `.git`** → 失敗，原因說明目錄非空且未納入版本控制 |
| 掛載有 `.git` 但不是有效 git repo → 失敗，原因明確 |
| 清單檔不存在或無法解析 → 失敗，指出解析錯誤 |
| **清單檔中某條目引用的來源內容在 repo 中不存在 → 失敗，原因指名該 uid 與路徑**（承接原 T1 的來源存在性；僅查來源側，目標未部署是合法狀態，不得因此失敗） |
| 白名單設定檔缺失或無法解析 → 失敗，原因明確 |
| 全部就緒 → 通過 |
| **失敗時以非零碼結束，不啟動服務** |

對應不變式 2：契約在做實事之前先自我驗證。

**空與非空要分開，因為它們是不同的狀況（#69）。** 空目錄是首次啟動的合法狀態：
volume 掛上了，還沒有人初始化過它。非空卻沒有 `.git` 則不是首次啟動——那裡有沒人審過的
檔案，而 `io/git.record` 的第一步是 `git add -A`，自動初始化等於把它們默默收編進第一次提交。
掛錯路徑會因此看起來像啟動成功。

「掛錯到一個**空**目錄」從容器內部與真正的首次啟動無法區分，這是事實。處置是把**解析後的
絕對路徑**印出來，讓看到訊息的人自己認得出來——訊息可行動，而不是假裝分得出來。

## 介面層

### T9 — HTTP 端點

以建好的容器測試，走真實 HTTP。

| 驗證的行為 |
|---|
| 每個端點的正常路徑回傳預期結構 |
| 驗證失敗 → 結構化錯誤（檔案、行號、欄位、建議），**不是純字串** |
| 進版端點：驗證失敗時**不產生變更紀錄也不寫出**（原子性） |
| **進版寫出 N 份、第 k 份失敗 → 前 k-1 份已寫出的目標檔案還原為進版前內容、全部已產生的變更紀錄一併撤銷**，容器內最終狀態與進版前逐位元組相同（承接 T18 移出的批次原子性） |
| 第二個編輯階段被拒，回覆含持有者姓名、email、開始時間 |
| 部署模式下逾時後階段自動釋放 |

### T10 — CLI

CLI 是 HTTP 端點的 client（ADR-00000009），**其測試不重複驗證業務邏輯**。

| 驗證的行為 |
|---|
| 每個指令映射到正確的端點與參數 |
| 端點回錯誤時，CLI 以非零碼結束並印出可讀訊息 |
| 服務未啟動時，訊息明確指出服務未啟動（而非連線錯誤堆疊） |

### T11 — 瀏覽器端到端行為

以自動化瀏覽器操作真實的前後端，驗證**使用者看得到的行為**。

| 驗證的行為 |
|---|
| 輸入身分後可看到清單，各項狀態正確 |
| 納管一個檔案後，它出現在左側樹且狀態為一致 |
| 修改一個參數並儲存 → **存為草稿**；樹上出現草稿標記，目標檔案尚未改變 |
| 再改另一份並儲存 → 兩份草稿並存，進版按鈕顯示「進版 (2)」 |
| 按下進版 → **兩份一起送出**，各產生一筆變更紀錄；目標檔案改變 |
| 輸入非法值 → 該列標示錯誤，**儲存按鈕停用**；int 欄輸入小數被拒 |
| **double 型別參數存後，其值帶小數點**（`5` → `5.0`）——擋 ROS 型別錯誤的招牌行為 |
| 外部修改目標檔案後按「檢查差異」→ 該項顯示偏離，可進入差異檢視 |
| 偏離時選「以來源覆蓋」→ 目標內容還原，狀態回到一致 |
| 偏離時選「將目標現況納入來源」→ 來源更新且產生紀錄；**若目標內容違反驗證則被拒** |
| 偏離時選「**先納入、待修正**」→ 目標現況載入草稿；**若含非法值，橫幅與該列即時警告（原因＋正確寫法），進版按鈕停用**，改乾淨後可進版 |
| 退版後參數回到先前值 |
| 開第二個分頁 → 顯示唯讀，並指出持有者 |
| 部署模式閒置逾時 → 自動退出且階段釋放 |
| **一般使用者模式下，型別欄為純文字**、白名單與屬性編輯入口**不顯示**（非停用） |
| 切換為開發者後，上述元素出現 |
| 搜尋範圍下拉選「參數名稱」後，只命中參數名稱 |
| 修改群組並儲存 → 左側樹立即重建 |
| list 參數可新增、移除、**以 ↑↓ 調整順序**，順序變更後儲存生效 |
| 歷史列表**不出現 `cfg`／`revert`／`import` 等內部代號** |
| 型別指定後該列顯示「已指定」，清除後回到推斷值 |
| **有未進版草稿時退出 → 二次確認並說明草稿將遺失** |
| 身分輸入頁的角色切換明顯可見（不在選單內） |

**測的是行為，不是 DOM。** 選取元素以語意屬性為準，詳見 `doc/UI-ELEMENTS.md`。

## 驗收層

系統層問「這個功能運作正確嗎」，驗收層問「**使用者能達成他的目的嗎**」。

差別具體在哪：系統層的每一步都通過，但**步驟順序讓人卡住**時，系統層測不出來。

### A1 — 把一份新 config 納入管理

| 旅程步驟 | 通過條件 |
|---|---|
| 開啟系統、輸入身分 | 不需要密碼或事先設定 |
| 找到那份檔案 | 從介面就能瀏覽檔案系統，不需先知道完整路徑 |
| 路徑不在白名單 → 被拒 | **錯誤訊息直接提供加入白名單的入口**（開發者）或說明需聯繫誰（一般使用者） |
| 檔案含歧義寫法 | 列出清單並要求確認，**不阻擋匯入** |
| 完成 | 該項目出現在左側樹、狀態為一致、**原始檔案內容未被改動** |

**失敗判準**：任一步需要離開介面（改設定檔、下指令、問人）即為不通過。

### A2 — 調整參數並進版

| 旅程步驟 | 通過條件 |
|---|---|
| 找到那個參數 | 搜尋參數名稱即可定位，不需先知道它在哪個檔案 |
| 修改 | **以輸入框修改，不需要知道 YAML 語法** |
| 輸入超出範圍的值 | 該列即時標示，儲存按鈕停用 |
| 改回合法值並儲存 | **存為草稿**；樹上出現草稿標記，目標檔案尚未改變 |
| 再改另一份 config 並儲存 | 兩份草稿並存 |
| 按下進版 | **兩份一起送出**，各產生一筆紀錄；註解未遺失 |
| 確認改了什麼 | 歷史中可見改了哪個參數、從什麼變成什麼、誰改的 |

### A3 — 發現並處置一次偏離

| 旅程步驟 | 通過條件 |
|---|---|
| 開啟系統 | **不需主動掃描即看到警示** |
| 理解發生什麼 | 橫幅說明該修改未經介面進行、沒有作者資訊 |
| 判斷 | 並排比對看得出改了哪些參數 |
| 處置 | 三個選項（以來源覆蓋／將現況納入來源／先納入待修正）的後果在按下之前就說明清楚 |
| 現況含非法值 | 「將現況納入來源」被擋並說明原因；改走「先納入、待修正」把現況載入草稿修正，**壞內容不進來源、也不靜默丟棄**（新增出口，2026-09-04） |
| 完成 | 狀態回到一致，且**處置本身留下紀錄** |

### A4 — 出錯後能自行修正

| 情境 | 通過條件 |
|---|---|
| 布林值寫成 `no` | 訊息指出行號、說明為何不接受、**給出正確寫法** |
| 重複的參數名稱 | 訊息列出**所有**出現位置 |
| 跨欄位規則違反 | 說明是哪兩個欄位衝突；可 override 但需填理由 |
| 通用 | **沒有任何錯誤訊息只說「格式錯誤」或「操作失敗」** |

**失敗判準**：使用者看完訊息後仍不知道下一步該做什麼。

### A6 — 開發者整理一份新納管的 config

| 旅程步驟 | 通過條件 |
|---|---|
| 切換為開發者 | 身分輸入頁上的切換明顯可見，不需尋找 |
| 找到那份 config | 它在「未分群」節點下，**不需要記得它叫什麼** |
| 設定群組 | 儲存後左側樹立即重建 |
| 更正型別 | 型別欄可改；改完標示為「已指定」 |
| 發現改錯了 | **可個別清除該欄位的指定**，不影響其他欄位 |
| 切回一般使用者 | 型別欄變回純文字，屬性編輯入口消失 |

**失敗判準**：任何開發者專屬功能在一般使用者模式下**顯示但停用**。

### A5 — 未受訓者可自行操作（人工）

**無法自動化。** 由未參與開發的同事在無人指導下，依序完成 A1 至 A4；
由另一位開發者完成 A6。全程不得詢問操作方式。

這是 v0.9.0 的驗收條件。前四項可腳本化，這一項不行——**能不能自己摸索出來，
只能由真的沒摸索過的人來測**。

## 工具層（repo 自身的守門腳本）

### T19 — 守門腳本的規則

**介面**：每支 lint 的命令列。餵一個目錄或 base ref 進去，觀察**結束碼與訊息**，
不碰腳本內部。規格以 bats 撰寫，放在 `test/bats/unit/<腳本名>.bats`。

| 腳本 | 規格 |
|---|---|
| `script/lint_adr.sh` | `test/bats/unit/lint_adr.bats` |
| `script/lint_commit.sh` | `test/bats/unit/lint_commit.bats` |
| `script/lint_paths.sh` | `test/bats/unit/lint_paths.bats` |
| `script/lint_portability.sh` | `test/bats/unit/lint_portability.bats` |

**每條規則都要有一個會觸發它的案例。** 一支所有 FAIL 路徑都沒被執行過的 lint，
它擋得住什麼是沒有證據的——規則看起來在運作，而那正是回歸風險最高的形狀。
`shellcheck` 不能充數：依 `doc/test/TEST.md` 那是軸 1 靜態分析，不是動態測試。

**WARN 的案例要斷言結束碼為 0。** fail 與 warn 的差別就是擋不擋得住合併，
只斷言「訊息裡有 WARN」不會發現一條被誤寫成 fail 的 warn。

**規格必須通得過突變檢查。** 把它針對的規則從腳本裡拿掉，該規格要轉紅。
不會因規則消失而轉紅的規格，測的不是那條規則。這一項不自動化，
在 PR 描述裡記下做過哪些突變與結果。

**已知未涵蓋**：`script/test.sh` 的「缺工具不得靜默通過」保證（#72），
以及其餘 shell 腳本（#74）。兩者都不是刻意留空，是還沒做。

## 撰寫規則

- **紅燈先行。** 先寫會失敗的測試，再寫剛好讓它通過的程式碼。
- **一次一片。** 一個測試介面、一個測試、一個最小實作。
- **垂直切片，不橫向切片。** 不先寫完全部測試再實作。
- **重構不在迴圈裡。** 它屬於 review 階段。
- **期望值必須來自獨立來源**，不可用與實作相同的方式重算。
- **一個測試一個邏輯斷言。**
- **測試名稱描述「做得到什麼」而非「怎麼做」**，並使用 `CONTEXT.md` 的用語。

## 與版本里程碑的關係

版本驗收檢查點是**結果**，本文件的測試介面是**觀察位置**。

一個版本的實作是**多輪垂直切片**，直到該版本的驗收檢查點通過。
**不是「先寫完該版本的所有測試再實作」**，那正是橫向切片的反模式。
