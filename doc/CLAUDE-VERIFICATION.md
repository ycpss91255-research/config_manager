# Claude 開發者驗證與修正清單

收到「驗證專案」「依清單修正」或使用者回報 `Uxx` 時，依本文件執行。使用者操作與預期結果的唯一清單是 [USER-VERIFICATION.md](USER-VERIFICATION.md)；沿用其編號，不另造一套通過標準。

**範圍內的錯誤必須修正並重驗，不能只列問題、提出建議或要求使用者自行改程式。** 功能缺失必須記為未完成；只有實作、相關驗證及原操作重驗都完成，才能改成通過。建立本文件本身不代表已執行驗收，也不是立刻開發全部里程碑的指令。

## D01 — 確認範圍、基準與需求

- [ ] 先讀 `CLAUDE.md`、`CONTEXT.md`、`doc/PRD.md`、`doc/TEST-PLAN.md`；遇到相應功能，再讀 `doc/UI-ELEMENTS.md`、相關 ADR 與里程碑／issue 驗收條件。
- [ ] 記下日期、分支、commit、未提交修改、容器映像與執行模式。保留使用者既有修改；修正工作依專案規範使用功能分支。
- [ ] 使用者指定 U 編號時，處理該項及受影響回歸；指定版本時，處理該里程碑及前置能力。只說「驗證專案」時，先驗現有能力並列出完整產品缺口，依既有里程碑順序處理，不自行把所有未來版本併入同一修正。
- [ ] 為本輪每個 U 編號標記：待驗、失敗、未完成、阻擋、通過或範圍外。缺少功能不能標「不適用」來提高通過率；範圍外仍保留於缺口清單。
- [ ] 對照實際程式、已議定規格與實際執行結果。文件內的「已落地／尚未落地」可能過期；衝突要查證並指出具體位置，不以註解或檔案存在作成功證據。

完成條件：本輪 U 編號、需求來源、目前缺口及測試環境均已明確。需求衝突需要 owner 決策時，記下衝突及選項，繼續其他不受影響的項目。

## D02 — 準備可重現的使用者環境

- [ ] 準備獨立的來源 repo、目標資料夾、白名單外資料夾與容器掛載。目標只用副本；故障模擬、刪檔、權限修改、重啟與復原不作用於正式設備。
- [ ] 填寫使用者清單的準備表，交付可開啟的網址、具名範例及操作起點；不要把環境建置留給使用者猜。
- [ ] 建立 YAML／JSON／TOML／INI／raw 的範例，保留原始 bytes、摘要、權限與 Git 基準；另建歧義、語法錯誤、重複 key、schema 及跨欄位規則範例。
- [ ] 需要故障、外部修改、缺檔、連結逃逸或多人操作時，先準備情境與恢復方式。證據遮蔽敏感值，仍須保留足夠資訊供重現。

完成條件：使用者不需寫程式即可開始 U01；每個異常案例都有具體資料與可恢復的操作步驟。

| U42–U43 | 記錄真人操作及實際兩週使用證據，修正途中發現的問題 | A5、v0.9.0／v0.10.0 檢查點 |

另外必須核對的底層行為：

- [ ] **驗證分層**：歧義值可確認後原樣納管，不能錯改成進版時也放行。進版硬擋第一／二層錯誤；跨欄位警告的覆寫需理由。重複 key 指出全部位置；每個錯誤有檔案、位置與修正建議。（T3、T12、A1、A4）
- [ ] **格式保留**：對支援格式核對未改動時的逐位元組往返，以及參數編輯後未觸動部分保留。JSON／INI 存原文的能力不等於已具備編輯後保格式能力。（T6）
- [ ] **真實 I/O**：Git 整合測試使用真 repo；寫出故障不留半檔，回復失敗要報殘留；只 stage 本次修改，不能夾帶不相關檔案。（T7、T8、T9）
- [ ] **啟動與資料完整性**：清單 uid／來源／目標重複、來源缺失、非法路徑、未知格式及不可解析白名單會具體報錯；啟動失敗不能顯示服務已就緒。（T1、T15、T23）
- [ ] **HTTP 與 CLI**：相同功能走相同 API 規則；一般使用者直接送請求也不能執行開發者專屬動作。角色仍是自我宣告，不能宣稱已提供密碼認證。（T9、T10、T17）
- [ ] **部署與時鐘**：依規格驗證開發／部署差異，後端判定環境；自動化逾時案例使用既有可注入時鐘介面，人工驗收另外保留實際 UI 證據。（T13）
- [ ] **發布範圍**：要求核心流程完成時，同時驗證網頁與純 CLI 的納管→修改→退版→偏離→處置。要求完整產品時，逐條覆核 `doc/acceptance-checkpoints.toml` 中對應里程碑，不能只驗本表可見畫面。

完成條件：每個範圍內項目都有實際結果；畫面行為與必要的來源、目標、歷史證據相符。

## D04 — 有錯就修，修完重驗

對每個失敗項目依序執行：

1. **重現**：保留 U 編號、輸入、步驟、預期、實際、錯誤文字及修正前證據。若暫時重現不了，保留未解狀態並查使用者提供的情境。
2. **定位**：確認是產品實作、測試、環境接線還是過期文件。以既有需求及可觀察行為判斷，不把預期改成符合錯誤實作。
3. **修正**：在已議定測試介面補上能重現問題的回歸案例，先確認失敗，再做最小修正。涉及新測試介面時，依 `TEST-PLAN.md` 的既有議定流程處理；同一介面的新案例不需要重開介面確認。
4. **重驗**：跑原失敗案例、受影響回歸，以及原 U 項的完整使用者操作。API 測試通過不能替代瀏覽器流程；mock 成功不能替代真實檔案／Git 效果。
5. **交付**：記下改動檔案、commit（尚未提交就明示）、修正前後證據及重驗結果，交回使用者複驗。開發者驗證結果不直接替使用者勾選其清單。

範圍內缺失的功能按所屬 milestone／issue 補齊；若前置需求尚未定案，指出具體依賴並繼續可獨立完成的工作。環境工具、權限或網路阻擋時記錄已嘗試的命令與錯誤，不宣稱通過，也不只寫「待確認」後遺漏該項。

完成條件：原問題已消失、回歸檢查通過，或未解項目具名保留且說明真正阻擋原因。未解項目存在時不能宣稱全數完成。

## D05 — 執行專案檢查並保留完整結果

依專案規範在容器中執行檢查。現有入口如下；參數以腳本 `--help` 及 justfile 為準：

```bash
# 修正中先跑相關規格，將路徑換成實際檔案
just test file test/pytest/system/test_web.py

# 完成程式修正後執行全套 lint、測試與覆蓋率閘門
just test

# 指定里程碑驗收；將版本替換成本輪範圍
./script/acceptance.sh v0.2.0
```

- [ ] 保存實際命令、結束碼、測試數、失敗／略過項目、完整 log 路徑及四個區域的覆蓋率結果。門檻讀 `pyproject.toml`，不在此另訂一份。
- [ ] 對照表 `specs = []` 代表未涵蓋；測試存在但沒連到檢查點時，核對行為後修正對照。對應完整檢查點的所有要求都有證據才可連線，不能掛一個無關或只涵蓋部分行為的測試消紅。
- [ ] 發現過期的實作狀態或對照原因，修正在原有 owner 文件中；本清單不建立第二份永久實作狀態表。
- [ ] 遵守既有 CI／分支規範。完整檢查通過後，除非又有修改、失敗或未解疑慮，不重複執行同一套檢查。

禁止把降低門檻、略過失敗案例、吞例外或假成功回應當成修正。純文件修改做連結、編號及內容核對即可，不為此建立模仿文件內容的自動測試。
