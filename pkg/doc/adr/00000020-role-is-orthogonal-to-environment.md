# Role and environment are orthogonal concepts

> 服務：不變式 4（預設值落向安全）＋ 不變式 5（兩分支預設規則）

- **Date:** 2026-09-02
- **Status:** Accepted
- **Relates to:** ADR-00000014

## Context

有三類操作的後果與一般的參數調整不同：修改參數型別（改錯會讓後續所有寫入用錯誤的
形式，直到 node 啟動失敗才發現）、維護白名單（決定系統能碰主機上的哪些目錄，是安全邊界）、
編輯 config 屬性（群組決定整個面板的組織方式，誤改會讓其他人找不到熟悉的位置）。

這三類不該對所有使用者開放。問題是：以什麼區分。

## Decision

**角色與環境是兩個正交的概念。**

| 概念 | 誰決定 | 影響 |
|---|---|---|
| 角色（一般使用者／開發者） | 使用者在身分輸入時自行選擇 | **能做什麼** |
| 環境（開發／部署） | backend 依部署階段判定，前端無法變更 | **階段行為** |

角色於 v0.10.0 前為**自我宣告**，身分輸入頁上一個明顯的切換，沒有驗證。目的是
**讓使用者清楚知道自己處於哪個模式**，而非阻擋。

僅開發者可用的元素在一般使用者模式下**直接不顯示**，而非顯示後停用。

## Alternatives

- **把三類操作綁在開發環境上**：部署環境下仍可能需要開發者調整白名單——例如現場
  新增一份 config 而其路徑不在白名單內。綁在環境上時這件事做不到。
- **只有一種角色，全部開放**：改錯型別的後果是靜默的，不該讓現場調參的人有機會誤觸。
- **實作真正的認證**：本系統明確不做認證。若需要，應在反向代理層處理。
- **顯示但停用**：使用者會以為自己權限不足，實際上只是沒切換角色——而切換就在眼前，
  沒有任何阻擋。這會製造不存在的挫折。

## Consequences

- 介面需要維護一份角色對照表，且該對照表本身要被測試（測試介面 T17）。
- **測試驗證的是對照表正確，不驗證「無法偽造角色」**——v0.10.0 前沒有那個保證，
  也不假裝有。
- 「記住此裝置」不記住角色，每次開啟都要重新選。
- 錯誤訊息需依角色分歧：開發者看到直接入口，一般使用者看到「請聯繫開發者」——
  **後者仍然說清楚下一步是什麼**。
