# Tests are written only at pre-agreed interfaces

> 服務：不變式 7（維持嚴謹且與業界對齊的測試門檻）

- **Date:** 2026-09-02
- **Status:** Accepted
- **Relates to:** ADR-00000011

## Context

實作採測試先行（red → green）。此方法有一個前置條件常被略過：**測試要寫在哪裡。**

先前的設計文件定義了三件事——測試放哪（目錄結構與分類）、每個版本要驗收什麼
（結果層級的檢查點）、以及各模組的輸入輸出契約。但沒有任何一份定義了
**在哪個介面位置觀察行為、觀察哪些行為**。

沒有這份定義，測試先行會退化成兩種失敗形態之一：對著內部實作寫測試（重構就壞），
或是把力氣平均灑在所有邊界案例上（關鍵路徑反而覆蓋不足）。

## Decision

**測試介面**是「從哪個位置觀察行為」。同一段程式碼可以從很多位置觀察，
但只有公開介面這個位置是穩定的。

**沒有經過確認的測試介面，不寫測試。** 在寫任何測試之前，先寫下要測的介面並取得確認。

本專案議定十八個測試介面與六個驗收旅程（詳見 `doc/TEST-PLAN.md`）。同時明確列出
**不測的項目**，以及三個**刻意留空**的位置與其理由。

**刻意留空與漏掉的差別在於有沒有寫下理由。** 因此清單必須經過覆蓋率審計：
每個模組與每條流程都要落在至少一個測試介面上。

三個反模式列為禁止：**耦合實作**（模擬內部協作者、測私有函式、繞過介面從側面驗證）、
**套套邏輯**（期望值以與實作相同的方式重算）、**橫向切片**（先寫完全部測試再實作）。

**不使用 seam 這個外來詞。** 它多帶的那個意思（從哪裡觀察）用中文講得清楚。

## Alternatives

- **不預先定義，邊寫邊決定**：測不了全部，因此測試力氣會依當下的直覺分配，
  通常落在容易測的地方而非關鍵路徑。
- **只定義到系統層，驗收靠人工**：系統層驗證「功能運作正確」，但每一步都通過而
  **步驟順序讓人卡住**時，系統層測不出來。驗收層以完整的使用者旅程撰寫。
- **以檔案為單位要求覆蓋率**：驅使人為了數字去測私有函式與 getter，正是耦合實作反模式。
- **先寫完一個版本的所有測試再實作**：橫向切片。在理解實作之前就把測試結構定死。

## Consequences

- `doc/TEST-PLAN.md` 是實作前必須確認的文件，狀態為提案直到逐項確認。
- 新增測試介面需要更新該文件並取得確認，不能在實作中途臨時增加。
- 版本驗收檢查點（結果）與測試介面（觀察位置）是不同層次：一個版本的實作是多輪
  垂直切片，直到該版本的檢查點通過。
- 「不測的項目」同樣需要記錄。
