# config-manager — Product Requirements

集中式 config 管理系統。本文件只放**產品不變式**：必須恆常維持的性質。
機制、實作與取捨記在 `doc/adr/`；領域用語記在 `CONTEXT.md`。

**任何 ADR 都不得違反本文件的不變式。** 違反的設計不是取捨，是缺陷。

---

## 問題

Config 散落系統各處（`/opt`、`/etc`、ROS 套件內），無集中清單；修改後無法
判斷改了什麼、誰改的、何時改的，也無法回到先前狀態；YAML / JSON 的型別與
縮排陷阱多，直接以文字編輯器修改風險高。

## 目標

單一介面作為 config 修改的唯一正規入口，以 git 為版控核心，修改前經自動
驗證，並能偵測繞過介面的直接修改。

---

## Core Invariants

### 1. 每個容器只跑一個服務

系統由數個容器組成（frontend、backend），每個容器只負責一個服務。服務之間
透過明確的網路介面溝通，不共用程序空間。

背景工作不得塞進既有容器——那會使該容器變成兩個服務。自動重啟策略只發給
真正的服務；工作階段容器（開發、測試）不發。

### 2. 絕不靜默失敗

任何錯誤、缺失或不相容的設定都必須**大聲且提早**失敗，絕不是仍然顯示成功
的靜默跳過。契約在做實事之前先自我驗證。

通用檢驗：任何「系統自動幫使用者處理掉」的設計都需重新檢視——**它是在消除
麻煩，還是在消除訊號？**

### 3. 可擴充為多實例

資料模型不得寫死無法跨實例共存的字面值。這是一條前瞻保證：未來擴充到多台
機器時，不會撞牆而必須回頭改既有結構。

### 4. 預設值落向安全

當預設值有「安全 vs 方便」的張力時，落向安全，較危險的選項為 opt-in。

### 5. 預設值由兩個問題決定，不由個人偏好

一個功能開關要不要預設打開，問兩個問題：

1. 打開它，會不會讓原本正常運作的東西變得不正常？會 → 預設關。
2. 忘記打開它，會不會出事？會 → 預設開。

只有兩者同時成立才預設開；其餘一律預設關。

**與不變式 4 的分工**：不變式 4 說的是**傾向**（衝突時往哪邊倒），這一條說的是
**程序**（怎麼判斷）。先問這兩題；若結果衝突或都不明確，再用不變式 4 決定往哪邊倒。

### 6. 一個真實來源，向外傳播，而非平行維護 N 份副本

任何一份資料只有一個 owner。

此不變式同時是**產品命題**：config-manager 就是把這個模式從程式碼傳播套用
到 config 傳播——**來源 repo 是唯一真實來源，目標位置的檔案是產物**。任何
「以磁碟現況為準」的邏輯都違反此原則。

### 7. 維持嚴謹且與業界對齊的測試門檻

承諾本身是不變式；具體的分類法與覆蓋率工具是可置換的機制。

### 8. 身分與命名一次解析，來自檔案

命名的分歧來自明確的、檔案記錄的 override，絕不來自環境變數，也絕不來自
目錄名或主機名的意外。

兩種失效模式都是無聲的，代價是已經看起來完成的工作。

### 9. 文件由程式碼推導，不在旁邊複製一份

可從樹推導出來的數字或清單，在被閱讀時計算，不存進一份需要有人手動維持
一致的追蹤檔案。文件裡放的是任何產生器都做不出來的東西：意圖、理由、以及
一個東西為何是這個形狀。

一份看起來權威但已過期的文件，就是不變式 2 的靜默失敗被寫進文件裡。
